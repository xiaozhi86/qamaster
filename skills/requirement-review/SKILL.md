# ★ Runtime 控制协议（最高优先级·模型无关·必读）

> **流程控制权不在模型，在 Runtime。** 本 skill 的业务规范（本文件）由 Python 状态机 `runtime/qamaster_runtime.py` 驱动执行；无论底层是什么模型，0→1→…→7 阶段顺序由状态机裁决，模型只负责当前阶段的思考与产物。

## 你的角色

你是 **LLM Worker**：只在 Runtime 颁发的【RUNTIME CONTRACT 契约卡】范围内思考与产出。你**无权**：决定下一阶段、宣布阶段完成、跳过人工门禁、修改流程状态。

## 入口协议（bootstrap → start，单步不变·模型无关）

> `/requirement-review` 命令文件内部链式跑两步，用户无感；模型只接收 Runtime 颁发的契约卡。

1. **bootstrap**（由命令文件跑）：从用户输入（文件路径/内联文本）派生**需求标识 `req_id`**——文件取首个 `# ` 标题清洗，内联取首个非空行；与在途需求/已归档索引去重，碰撞加 `-YYYYMMDD`。**不创建状态**（幂等可重跑）；检测到进行中状态则输出 `RESUME`，`start` 走 resume 分支不重建。
2. **start --req-id <id>**（由命令文件跑）：req_id 必需且恒非空；状态落 `.qamaster/requirement-review/<req_id>/state.json`；启动或断点续跑；输出 Phase 0 契约卡。

**模型不派生 `req_id`**：Phase 0 起所有产出物文件名直接用 `state.req_id`（来自 bootstrap），不再在阶段内派生 id——消除"先有鸡还是先有蛋"。重跑 `/requirement-review` 同一在途需求：bootstrap 输出 `RESUME` → `start` 续跑，断点不丢。

## 每轮执行循环（强制）

```
读契约卡（start/next/status 的输出）
  → 按 ALLOWED 执行当前阶段，产出 PRODUCES
  → 运行 python "runtime/qamaster_runtime.py" gate --workflow requirement-review --req-id <id>
       PASS → 运行 next --workflow requirement-review --req-id <id> 取下一阶段契约卡
       FAIL → 按修复指令原地修复，重跑 gate（禁止跳阶段）
  → 人工门（Phase 4 用户确认）：输出确认请求后停止等待用户；
     用户答复后先落盘再 gate；确认用 confirm --workflow requirement-review --req-id <id>
     反馈问题用 fail --to <阶段> --workflow requirement-review --req-id <id> --reason "..."
```

## 铁律

1. **状态以 Runtime 为准**：每次接到用户新消息，先运行 `python "runtime/qamaster_runtime.py" status --workflow requirement-review --req-id <id>` 恢复权威状态，禁止凭对话记忆推断"现在该哪一步"。
2. **门禁以机器判定为准**：`gate` 的 PASS/FAIL 由确定性检查给出；禁止模型自证"已通过"（声明≠核实）。
3. **MANIFEST 由 Runtime 维护**：`requirement-review-out/MANIFEST.md` 是多需求共享索引，由 Runtime 在 gate PASS 时自动维护（Phase 0 `add` / Phase 1 `update` 评审问题清单 / Phase 5 `update` 最终需求文档 / Phase 7 `complete`）。模型**禁止 Write/Edit MANIFEST.md**。失步时执行 `python runtime/qamaster_runtime.py manifest reconcile` 重建。
4. **业务规范不变**：Runtime 只做流程控制；专家 Agent 评审标准、输入协议、输出协议等全部业务规则仍以本文件为唯一细则来源。**流程由 Runtime 严格控制、与模型无关。**

①【BA Agent（业务分析）】

  **BA Agent（业务分析）评审标准（Expert Level）**：

  👉 核心：业务完整性 + 正确性 + 闭环性

  1. 业务目标与价值（Business Objective）
  
    是否定义明确业务目标（目标用户 + 场景 + 价值）
    是否具备可衡量指标（如转化率、成功率、时效）
    是否与组织/项目战略一致
  2. 业务范围与边界（Scope & Boundary）
  
    是否清晰定义In Scope / Out of Scope
    是否明确上下游系统边界
    是否识别外部依赖（系统/人工/第三方）
  
  3. 业务流程完整性（Process Integrity）

    是否覆盖：
      主流程（Happy Path）
      分支流程（Alternative Flow）
      异常流程（Exception Flow）
      逆向流程（撤销/回滚）
      是否存在流程断裂或不可达路径
  4. 业务规则完备性（Business Rules）

    是否定义所有关键决策规则（条件/约束/计算）
    是否存在隐式规则未显式表达
    是否存在规则冲突或优先级不明确
  5. 角色与职责（Actors & Responsibilities）

    是否定义所有参与角色
    是否明确角色权限与行为边界
    是否存在职责冲突或遗漏
  6. 数据语义一致性（Data Semantics）

    核心业务对象定义是否一致（订单/用户等）
    是否存在歧义字段或多义术语
    是否有统一口径（Single Source of Truth）
  7. 异常与边界（Exception & Edge Cases）

    是否覆盖异常输入、失败场景
    是否定义处理策略（重试/终止/补偿）
    是否考虑极端情况（高频/空值/重复）

②【PM Agent（产品设计）】

  **PM Agent（产品设计）评审标准（Expert Level）**:

  👉 核心：功能设计质量 + 一致性 + 完整性

  1. 功能必要性（Feature Justification）

    每个功能是否有明确用户价值
    是否存在冗余或重复功能
    是否符合最小可行原则（MVP）
  2. 功能完整性（Functional Completeness）

    是否覆盖用户任务闭环
    是否存在关键步骤缺失
    是否支持任务成功/失败路径
  3. 状态模型（State Machine）

    是否定义完整状态集合
    是否定义状态转换条件
    是否避免非法状态或死循环
  4. 交互逻辑（Interaction Logic）
  
    用户路径是否清晰、无歧义
    是否支持中断/恢复/取消
    是否存在不可达或重复路径
  5. 一致性（Consistency）
  
    命名一致（字段/按钮/状态）
    行为一致（相同操作一致反馈）
    设计模式一致
  6. 边界处理（Boundary Handling）

    空数据/极值/异常输入是否处理
    是否定义默认值/兜底策略
  7. 可扩展性（Extensibility）
  
    是否支持后续功能扩展
    是否避免强耦合设计

③【QA Agent（测试设计）】

  **【QA Agent（测试设计）】评审需求时必须输出**：

    1. ❌ 不可设计测试用例的需求点（必须指出）
    2. ⚠ 测试设计困难点（边界不清/状态不明）
    3. ✅ 可直接转测试用例的优质需求点

    4. 针对每个问题：
      - 影响的测试设计方法（如无法做边界值）
      - 补充建议（如何改需求）

  **QA Agent（测试用例设计专家视角）需求评审标准**：

  👉 核心一句话：
  这个需求文档，能不能被转化为：高质量、全覆盖、可执行、可自动化的测试用例？

  一、需求“可用例化能力”（Test Case Derivability）

  1. 需求是否可拆解为测试点

    是否可以清晰拆出测试点（Test Points）
    是否存在“一段话无法拆分测试点”的情况
    是否混合多个逻辑导致不可拆分

    👉 判定标准：

      ❌ “系统处理用户请求” → 不可测试

      ✅ 明确行为 + 条件 + 结果 → 可测试

  2. 是否具备“输入 → 处理 → 输出”结构

    输入是否明确（参数、条件）
    处理逻辑是否清晰
    输出是否具体（字段/状态）

    👉 否则问题：

      - 无法设计步骤
      - 无法写预期结果

  3. 是否支持“用例映射”

    是否能建立：
      需求点 → 测试点 → 用例
    是否存在：
      无法映射的需求描述
      多义描述

二、测试点覆盖可推导性（Test Coverage Derivability）

  1. 是否支持覆盖三大路径

    需求是否明确支持推导出：

      正常路径（Happy Path）
      分支路径（Alternate）
      异常路径（Exception）

    👉 如果需求只描述“正常情况”：
    ❌ 不合格

  2. 是否可推导边界条件（关键）

    是否定义：
      数值范围（最小/最大）
      长度限制
      枚举范围

    👉 否则：

    无法做边界值测试
  3. 是否可推导异常输入

    是否定义非法输入行为：
      空值
      格式错误
      越界值

    👉 否则：

      无法设计负向用例
  4. 是否支持状态测试

    是否定义状态（如：待支付/已支付）
    是否定义状态流转规则

    👉 否则：

    无法设计状态迁移用例

三、预期结果可验证性（Expected Verifiability）

  1. 结果是否明确（最关键）

    是否明确：
      返回字段
      状态变化
      提示信息

    ❌ 错误示例：

      “系统处理成功”
      “提示正确”

  2. 是否可验证（可观测）

    是否可以通过：
    页面
    接口
    数据库
    验证结果

    👉 如果：
    无法观测 → 不可测试
  3. 是否避免模糊词

    检查是否存在：

      合理
      正确
      快速
      适当

    👉 出现即：
    ❌ 必须整改

四、测试设计方法可应用性（Design Technique Applicability）

  👉 这是“专家级关键能力”

  1. 是否支持等价类划分

    输入是否可分类：
      有效类
      无效类

  2. 是否支持边界值分析

    是否存在明确边界
  3. 是否支持判定表（复杂逻辑）

    是否存在多条件组合逻辑
    是否明确所有条件
  4. 是否支持状态迁移测试

    是否定义完整状态机

  👉 结论：
  如果需求不支持以上方法：

  ❌ = 测试设计能力受限
  ⚠ = 高风险需求

五、测试步骤可构造性（Step Constructability）

  1. 是否可推导清晰操作步骤

    是否能明确：
    用户做什么
    系统响应什么
  2. 是否存在“隐式步骤”

    是否需要测试人员自行猜测流程
  3. 是否支持不同角色操作

    是否明确角色行为
六、测试数据可设计性（Test Data Designability）

  1. 是否定义数据约束

    类型（string/int）
    长度
    格式
  2. 是否支持数据组合
  
    多字段关联逻辑是否清晰
  3. 是否存在“隐式数据规则”

    未说明但必须满足的数据条件
七、异常与反向场景可推导性（Negative Designability）

  👉 体现测试专家能力

  1. 是否支持设计负向用例
  
    错误输入
    非法操作
    权限错误
  2. 是否定义异常处理逻辑

    失败后系统行为
  3. 是否支持“破坏性测试”

    是否可以构造极端场景
八、用例独立性支持（Independence）

  1. 是否支持用例独立执行

    是否依赖前置复杂流程

  1. 是否存在强耦合流程

    多步骤强依赖
九、自动化适配能力（Automation Suitability）

  1. 是否具备稳定输入输出

    是否可重复执行

  1. 是否避免人工判断

    是否需要“人工观察判断”

  1. 是否适合接口级验证

    是否可以脱离UI验证
十、缺陷发现潜力（Defect Detection Potential）

  👉 专家级核心

  1. 是否暴露高风险区域
  
    核心逻辑是否清晰

  1. 是否容易遗漏测试点

    是否存在隐含逻辑

  1. 是否支持“反例思维”

    是否可以验证：
      系统不该做什么

④【Arch Agent（技术架构）】

  **Arch Agent（技术架构）评审标准（Expert Level）**：

  👉 核心：可实现性 + 稳定性 + 可维护性

  1. 技术可行性（Feasibility）

    是否存在不可实现或高成本实现点
    是否依赖不稳定技术
  2. 架构一致性（Architecture Alignment）

    是否符合现有架构规范
    是否破坏系统分层/边界
  3. 接口设计（API Design）

    是否定义输入/输出/错误码
    是否满足幂等性
    是否具备版本控制策略
  4. 数据设计（Data Design）

    是否满足范式或性能要求
    是否避免冗余或数据不一致
    是否定义数据生命周期
  5. 性能与扩展（Performance & Scalability）

    是否考虑并发/吞吐
    是否存在性能瓶颈
    是否支持横向扩展
  6. 容错与恢复（Fault Tolerance）

    是否有降级/重试/熔断机制
    是否支持失败恢复

⑤【UX Agent（用户体验）】

  **UX Agent（用户体验）评审标准（Expert Level）**：

  👉 核心：易用性 + 认知效率 + 体验一致性

  1. 任务效率（Task Efficiency）

    是否最少步骤完成任务
    是否减少用户操作负担
  2. 可理解性（Clarity）

    信息表达是否清晰
    是否避免歧义或认知负担
  3. 反馈机制（Feedback）

    操作是否即时反馈
    错误是否可理解、可恢复
  4. 容错性（Error Tolerance）

    是否允许用户犯错并恢复
    是否提供撤销/确认机制
  5. 一致性（UX Consistency）

    是否符合平台/行业习惯
    是否统一视觉和交互
  6. 可访问性（Accessibility）

    是否考虑不同用户能力
    是否支持可读性/可用性标准

⑥【Risk Agent（风险控制）】

  **Risk Agent（风险控制）评审标准（Expert Level）**：

👉 核心：安全性 + 合规性 + 风险可控

  1. 业务风险（Business Risk）

    是否可能造成资金损失/业务错误
    是否存在规则漏洞
  2. 安全性（Security）

    是否存在认证/授权漏洞
    是否可能数据泄露
  3. 合规性（Compliance）

    是否符合法律/行业规范
    是否涉及隐私数据合规（如GDPR类）
  4. 攻击防护（Abuse Prevention）

    是否防止刷接口/恶意请求
    是否限制频率/重复操作
  5. 极端与故障场景（Extreme Cases）

    高并发是否安全
    系统异常是否有保护措施
  6. 风控策略（Risk Control Strategy）

    是否有监控/告警
    是否有风控规则（限流/校验/拦截）

⑦【Dev Agent（开发实现）】

  **Dev Agent（开发实现）评审标准（Expert Level）**：
  核心目标：

  确保需求文档对开发团队而言：

    可实现性明确
    功能与边界清楚
    技术实现风险低
    可维护、可扩展、可测试

  一、需求实现可行性（Feasibility）

    功能描述清晰
    是否有明确的输入、处理、输出？
    是否存在模糊或歧义描述？
    是否容易被误解或多种实现方式？
    技术可实现性
    现有技术栈是否支持实现？
    是否涉及高风险技术或难以实现的操作？
    是否需要额外技术调研？
    边界条件明确
    所有业务边界、条件、约束是否清楚？
    是否有未定义的边界行为？
    接口可实现性
    内部系统接口与外部系统接口是否清晰？
    输入输出格式是否明确？
    异常处理是否明确？

  二、数据设计可实现性（Data Design Realism）

    数据格式与类型
    所有字段类型是否明确（int、string、date 等）？
    数据长度、约束、格式是否明确？
    数据依赖关系
    是否有多表、多模块依赖？
    数据交互逻辑是否清晰？
    数据一致性
    是否支持事务要求？
    是否有潜在数据冲突或并发问题？

三、业务逻辑可实现性（Business Logic Implementability）

    逻辑完整性
    条件分支是否完整？
    是否存在逻辑冲突或遗漏？
    是否可以拆解为开发可实现的逻辑单元？
    边界与异常逻辑

第0阶段：输入预处理与降级（强制·必须在评审前执行）

> 当前部署模型为文本-only（报错 "Model only support text input" 即本约束触发）。
> 需求文档常含原型截图/流程图/扫描件/含图PDF，非文本内容直接喂模型会 400 硬崩。
> 本阶段把任何非文本输入统一转为纯文本，再喂专家团评审。规则契约单一事实源：config/input_rules.json。

执行步骤（按序，禁止跳过）：

1. 输入类型探测
   - 扫描用户提供的文件/粘贴文本，按扩展名识别类型：纯文本(.txt/.md/粘贴) / PDF / Word / PPT/Excel / 图片(.png/.jpg等)
   - 粘贴文本 → 直读，跳过本阶段后续
   - 纯文本文件 → 直读，跳过本阶段后续

2. 非文本输入分流抽取（经 scripts/extract_text.py，禁止直接把图喂模型）
   - PDF → pdfplumber 抽文本+表格+图片坐标，文本块+图片按 y 坐标交错就地回填；单页字符<阈值 → 扫描件 → pdf2image 逐页转图 → 整页 OCR（天然就位）
   - Word → python-docx 遍历 body 子元素抽正文+表格，内嵌图片就地 OCR 占位回填
   - PPT → python-pptx shapes 按(top,left)排序抽文本框+表格，Picture 就地 OCR 占位回填
   - Excel → openpyxl 抽单元格文本
   - 图片/截图/扫描件 → RapidOCR(中文 ch)
   - 命令：python scripts/extract_text.py <文件路径> --json
     （返回 来源/字符数/预处理方式/置信度/图片数/降级标记/摘要，不灌全文，降本）

3. 就地回填（强制·保留图文上下文语义）
   - 图片 OCR 文本须**就地回填**到图片在文档中的原始位置（占位符 `【图片@位置k(置信度)：文本】`），不得汇总到文末或丢失
   - Word 遍历 body 子元素、PDF 按 y 坐标交错、PPT 按 shape 坐标排序
   - PDF 复杂版式（多栏/坐标不可靠）降级：正文留位置标记 `→见图k@页n-yn`，OCR 文本汇总到文末 `【图k@页n：<OCR>】`

4. 模型能力探测与降级（核心·防400硬崩）
   - 若抽取阶段报 400 "Model only support text input" → 确认当前文本-only → 强制所有视觉内容走 OCR 转文本后再分析
   - OCR/解析依赖缺失 → 尝试 pip install 兜底 → 失败显式报错 + 用户指引（不静默放弃）
   - OCR置信度 < 阈值（疑似流程图/原型图，非纯文字）→ 回退：提示用户补充该图的文字说明
   - 扫描件PDF但 pdf2image/poppler 不可用 → 回退：提示用户转文字版或提供截图文字说明

5. 标准化文本需求产出
   - 抽取后的纯文本作为后续专家团评审的唯一文本输入
   - 回显抽取来源/置信度/降级标记（供用户复核抽取质量）
   - 超长文档(>24000 token) → 按章节/模块分块，分批喂评审Agent（不可超32000单响应上限）

6. 专家团路由（动态选专家·核心团恒参与·宁多勿漏）
   - 读 config/agents.json：核心团 core_agents（PM/QA/Dev）恒参与；扩展团（BA/Arch/UX/Risk）按三级裁决启用
   - ①信号词命中：需求文本命中该专家任一 required_signals → 必启用（确定性）
   - ②co_trigger 连带：Arch 或 Risk 命中 → BA 连带启用（资金/接口类需求共性缺口正是数据口径/业务规则/枚举，属 BA 主场）
   - ③语义兜底：未命中信号词但该视角仍有关键价值 → 启用并写明理由；仅当明确无关（如后端接口无 UI → UX）才裁掉
   - 默认偏向「存疑即启用、宁多勿漏」：漏选专家=漏掉整个评审维度，覆盖率优先于 token 成本
   - 专家团名单落盘 requirement-review-out/Agents_<需求标识>.md（逐行：Agent id + 中文名 + 命中依据/启用理由）
   - 名单必须含核心团 PM/QA/Dev（Runtime `contains` 门禁机器判定，缺失即 FAIL，禁止自证）
   - 名单外专家标准仅作仲裁参考，不单独出问题清单

强制：
- 禁止将图片/扫描件/含图二进制文档直接喂给文本-only模型
- 必须经脚本抽取为纯文本后再分析；抽取失败须显式降级提示，不得静默中断

🔒 Runtime 受控流程与多需求并行（模型不可绕过）

requirement-review 走与 case-design 相同的 Runtime 状态机（8 阶段 0-7），核心约束：

- **入口由命令文件拉起**：`/requirement-review` → `commands/requirement-review.md` 内嵌 bash，链式跑 `bootstrap → start`（`--workflow requirement-review`），模型只接收 Runtime 颁发的契约卡（详见本文件开头「Runtime 控制协议」）。
- **阶段推进由 Runtime 裁决**：模型只负责当前阶段的思考与产物，无权决定下一阶段、宣布完成、跳过人工门禁。
- **门禁 req_id 绑定**：Phase 0/1/5/7 的文件存在性门禁按 `REQ_{req_id}.md` / `ReviewIssues_{req_id}.md` / `ReviewedReq_{req_id}.md` 精确匹配——多需求并发评审时互不串扰（A 的产物不会误放行 B 的门禁）。
- **人工确认门（Phase 4）不可绕过**：用户未明确确认前，Runtime 拒绝推进到 Phase 5。
- **MANIFEST 自动维护**：`requirement-review-out/MANIFEST.md` 聚合索引由 Runtime 在 gate PASS 时自动维护，模型禁止 Write/Edit。
- **多需求并行评审**：同一工程可对多个需求分别 `start --req-id <id>` 并发评审，状态按 `(requirement-review, req_id)` 分区落盘，互不覆盖。
- **上下文预算提示（v0.11.13·建议性）**：契约卡末尾按需追加 `##CONTEXT_BUDGET##` 段（阈值门控）——估算工作集 token 越线或进入已知重输出阶段（Phase 5/6）时，给出「压缩 → PART 拆分 → 分响应」出口，会话上下文已长时可先 `/compact`（状态已落盘，压缩后 `status` 可恢复）。未越线时整段不出现。随时可跑 `context --workflow requirement-review --req-id <id>` 查工作集估算与累计输入/输出 token（qamaster 足迹，非模型真实会话 token）。
