### 事实来源标注与开发校对（提升规格可信度·强制）

SDD 中以下三块标注「事实来源」，并由 @开发 校对（开发拥有实现层的权威信息，文档状态机/异常阈值/接口契约常与实现有差异）：

| SDD 要素 | 事实来源 | 校对要点 |
| -- | -- | -- |
| State（状态机） | 实现状态机 vs 需求文档状态机 | 实际状态定义与合法/非法流转，以实现为准；文档状态机差异处须在用例反映 |
| Exception（异常） | 超时阈值/重试次数/补偿动作 | 实现细节，须由开发提供真实阈值/次数/间隔/动作 |
| Input/Output（接口契约） | 接口名/入参/出参/类型 | 真实字段名/类型，喂第8阶段测试数据，闭合 0.4 杜撰禁令 |

* 信息源：§5【技术实现摘要】（@开发提供）优先；未提供时由澄清台账（角色路由，见 `references/clarification.md`）向 @开发 征集
* 校对结果同步更新"规则建模"section 与受影响用例 G/W/T，保持三者一致（与"重走第4阶段须以已落盘规则建模+用例G/W/T为重建依据"机制天然衔接）
* 与运行模式正交：完整模式 @开发 校对后才进第5阶段；连跑/轻量模式以需求文档为假设继续，标注"待@开发校对状态机/异常/契约"

### 规则建模 section 来源标注（破自证循环·闭合 0.9·强制）

> 规则建模 section 沉淀为 `TestCases_<需求标识>.md` 的 section（见 `references/output_write.md` 追溯性 section），并供 `verify_cases.py` rule_coverage 校验"每类规则被用例覆盖"。该 section 由模型自写，**若无来源约束会被 rule_coverage 反向洗白为"已覆盖"**（根因：自证循环）。强制每条规则项标注来源，破该循环：

* 每条规则项须标注来源：`[来源:需求文档<章节号/章节名>/台账Q<序号>/假设A<序号>]`（三选一或多）
* 来源=需求文档：规则直接来自需求某章节（最可信）
* 来源=台账Q<n>：规则来自澄清台账用户已答复项（权威事实）
* 来源=假设A<n>：规则来自已登记假设（连跑/轻量 P2/P3，须回显进待确认问题与假设清单）
* 无来源标记的规则项 -> 疑似脑补规则，`verify_cases.py` 检查15 规则来源软提示，selfcheck 检查15 阻断（补来源或转问题/假设后重跑）
* 用例关联规则列引用 `R<序号>`/`TP<序号>` 时，对应规则/风险/测试点须有来源标记，形成"用例->规则->来源"完整链路（闭合 0.9 业务行为来源追溯）

#### 第3阶段出口机器 gate（规则来源·写前·内存内·有界自修）

> **根因**：规则无来源标记本是第3阶段就能机器判定、却原设计要拖到写前第11检查15 / 写后第13 才反向捕获，缺陷回流滞后。本 gate 在第3阶段规则建模完、进第4阶段前就地把"脑补规则"拦住。

* **时机**：第3阶段规则建模完、进第4阶段前，内存内执行（零文件操作）
* **调用**：对规则建模 section 的 `lines` 调 `scripts/verify_cases.py` 的 `check_rule_source(lines)`（line-based，无需 keystone；第3阶段无用例表，不调 `run_inmemory`）
* **判定与自修**（≤2 轮）：
  * 无来源标记的规则项 → 内存内补 `[来源:需求文档<章节>/台账Q<序号>/假设A<序号>]` → 重跑
  * 确无来源（需求文档与台账均无对应规则）→ **硬阻断**，转为台账Q（P0/P1）/假设A（P2/P3）登记入【待确认问题与假设清单】，不静默保留
* **通过**→进第4阶段；此时规则建模 section 已通过来源校验
* **运行模式正交**：连跑/轻量 P2/P3 可转假设登记放行（沿用现有机制），P0/P1 硬阻断仍停

# 13、Given / When / Then 规范

## 13.1 Given（前置条件）

必须明确：

### 用户状态
用户已登录 / 用户未登录 / 用户Token已过期

### 权限状态
普通用户 / 管理员 / 财务角色

### 数据状态
订单待支付 / 订单已支付 / 库存充足

### 系统状态
缓存存在 / 缓存不存在 / MQ正常

### 环境状态
第三方接口正常 / 第三方接口超时

## 13.2 When（操作步骤）

要求：一步一动作、明确测试数据、可自动化执行。

示例：
1. 打开订单创建页面
2. 输入商品编号A001
3. 输入购买数量100
4. 点击提交订单

### 步骤化子结构（优化）

复杂用例的 When/Then 若塞进单格会变成超大文本块，可读性差且 Excel 转换易乱。推荐采用步骤化子结构描述：

```text
步骤1：动作 = 打开订单创建页面
步骤2：动作 = 输入商品编号A001；预期 = 商品信息回显
步骤3：动作 = 输入购买数量100；预期 = 金额计算正确
步骤4：动作 = 点击提交订单；预期 = 接口返回200，订单状态为待支付
```

在表格单元格中以"步骤N：动作；预期"分行串联，保持一条用例一行，不拆行不合并单元格。

## 13.3 Then（预期结果）

必须覆盖：页面结果、接口结果、数据结果、状态结果、缓存结果、MQ结果、日志结果。根据场景按需选择。禁止过度断言。

### 断言完整性（#2·强制·防"测试通过却漏 bug"）

不完整 oracle（只断言响应、不断言副作用）是"测试通过却上线出 bug"的头号原因。状态变更类用例须**双重断言**：

* **状态变更类用例**（When 含 创建/支付/扣减/更新/删除/撤销/退款/发货 等会改变业务状态或数据的操作）的 Then **必须同时包含**：
  * 接口结果（HTTP 状态码/错误码/status 字段）——验证操作本身
  * 数据/状态结果（订单状态更新为已支付、库存数量减少N、余额变更）——验证副作用真实发生
* 仅断言"接口返回200"而不断言数据/状态副作用的用例判定不完整（检查13，见 `references/selfcheck.md`）
* `scripts/verify_cases.py` 软性提示：状态变更类用例 Then 仅含接口结果、缺数据/状态副作用

> 例：`When=创建订单`，错误 Then：`接口返回200`（缺库存扣减/订单状态断言）；正确 Then：`接口返回200且status=SUCCESS；订单主存储中订单状态为待支付；库存数量减少2`。

# 15.6 用例生成端强制约束（防类型单一化·防漏测·第8阶段）

用例生成（第8阶段）须遵循以下生成端约束（与校验端 `scripts/verify_cases.py` 闭环）：

* **方法→列映射**：测试类型/测试维度列必须按 `references/methods.md` 决策表"方法→列映射"填写，禁止单一类型覆盖（全"功能测试"即不合格）。`verify_cases.py` 测试类型种类<3 提示方法未落地。

* **关联规则含 ID**：关联规则列须引用风险ID/测试点ID（见 20.3），实现风险/测试点→用例精确追溯。

## 15.7 第8阶段出口机器 gate（强制·写前·内存内·有界自修）

> **根因**：原设计下 `verify_cases.py` 的客观机器检查**要到第13阶段（写后回读）才第一次跑**（`references/output_write.md` 第6步）。后果：第9去重/第10覆盖率/第11自查/第12展示全在**可能有机器可判缺陷的用例集**上做白工，写后才发现"测试类型<3/边界内=0/断言模糊/脑补行为"，回头重写整份 .md。本 gate 把机器检查前移到写前，使后续阶段作用在已通过机器校验的用例集上。

### 机制

第8阶段用例生成完、进入第9去重前，于**内存内**执行出口 gate（零文件操作，符合 `references/output_write.md`"落盘前零文件操作"铁律）：

1. **输入**：本轮将 Write 的**完整 .md 文本**（追溯性 section + 15列用例表）按行作为 `lines`——即 Write 的 `content` 本身；若 §5 已落盘 `case-design-out/REQ_<需求标识>.md` 或用户在 §5 内联提供需求文档，则读为 `req_doc_lines` 一并传入（启用 #4 反向需求追溯 + #5 业务行为 token 核对，与 Phase 13 第2参数语义一致）；皆无则 #4/#5 跳过
2. **调用**：调 `scripts/verify_cases.py` 的内存入口 `run_inmemory(lines, req_doc_lines=None)`（无需读源码，返回结构化 dict：hard_violations / soft 疑似 / coverage 统计 / traces 追溯）
3. **判定与自修**（有界循环，≤2 轮）：
   * `hard_violations` 非空（ID 跳号重复 / 测试类型·维度·等级越界 / 用例名称四段缺失 / 4 固定列错值）→ **内存内修**（确定性修复，如补序号、改正枚举、补固定列）→ 重跑本 gate
   * `soft` 疑似>0（断言可观测#4 / 存储合规#9 / 存储schema交叉#9增强 / 重复#6 / 过度设计#7 / 关联需求ID追溯 / 断言完整性#13 / 业务行为来源#5 / 规则来源#15）或 `coverage` 缺口（类型<3 / 高价值维度=0 / 状态机非法流转=0 / 边界4档缺 / 异常子类缺 / 规则·风险·测试点·接口追溯未覆盖）→ **内存内修**→重跑本 gate
   * **硬阻断**（机器判不了的"确无来源"）：杜撰存储（#9，需求未提供真实 schema 且命中杜撰正则）/ 业务行为确无来源（#5，行为信号不在需求文档且无 R/TP 引用且无假设标记）→ **不静默自修**，须转为待确认问题（P0/P1）或假设（P2/P3）登记入【待确认问题与假设清单】并回显给用户；其余可机器自修
4. **循环上限**：≤2 轮机器自修（机器可判项的修复是确定性的、置信度高，故上限小于 Phase 11 的 ≤3）；2 轮后仍有机器可判项未过 → 升级阻断，列入【测试设计缺口清单】停止（同 `references/review_gate.md` 门禁失败处理）
5. **通过**→进入第9阶段（去重）；此时用例集已通过机器校验

### 与第11阶段（写前 LLM 自查）的分工（防重叠循环·强制）

| 层 | 第8阶段出口 gate（本节） | 第11阶段 selfcheck |
| -- | -- | -- |
| 谁判 | `verify_cases.py` 客观 | LLM 主观 |
| 管什么 | 机器能判：4 断言可观测/6 重复/7 过度设计/9 存储/13 断言完整性/15 规则来源 + 覆盖统计 + 规则·风险·测试点·接口·需求追溯 | 机器判不了：5 数据一致性/10 自动化友好/11 AI可解析主观面/14 对抗生成遍 + 1/8/9/12/15 的阻断决策与转问题/假设 |
| 循环 | ≤2 轮（机器自修，独立计数） | ≤3 轮（主观+对抗，独立计数，见 `references/selfcheck.md`） |

* **不重叠**：第8 gate 修好后，第11对 4/6/7/13/15 客观面的复核降为"确认已过"（不触发冗余修复循环）；第11仍全量跑其主观面（5/10/11/14）与阻断决策
* **计数独立**：第8 gate 的 ≤2 轮与第11的 ≤3 轮**各自独立计数**，不共享、不嵌套，无无限循环风险

### 与第13阶段（写后回读）的分工（防重叠·强制）

* 第8 gate 在**内存内**跑全量 `run_inmemory`（写前）；第13在**落盘文件**上跑 `python verify_cases.py <file>`（写后）
* 第13**不缩范围**（仍全量）：因第11的检查14对抗生成遍**新增用例**可能引入新机器缺陷，第13回归必须能抓到
* 第13 soft-fail **不回触第8 gate 循环**：走现有"内存修+重新单次 Write 覆盖 ≤2次/文件"回归路径（`references/output_write.md` 第6步），受现有约束；第8 gate 通过 ≠ 第13 必过
* 方向性：第8（客观发现）→ 第11（主观+对抗）→ 第13（写后回归），非三遍 discovery

### 运行模式正交

* 完整模式：第8 gate 硬阻断；命中 P0/P1 硬阻断项停止转问题/假设
* 连跑/轻量模式：第8 gate 命中 P2/P3 → 假设登记放行（沿用 `SKILL.md 6.5` 自动放行机制），**gate 不放宽质量底线，只放宽"等人工"时点**；P0/P1 硬阻断仍停
* 重型/中型/轻型分级（`references/dedup_coverage.md` ch26）：第8 gate 全规模必跑（轻型不跳，与"自查11/审核14 不得跳过"一致）

### 设计约束（不可违背）

* `run_inmemory` 纯函数、零临时文件、零 Bash、零权限弹窗——与"内存内完成、落盘前零文件操作"哲学一致
* gate 输入 = Write 的 `content` 本身（同一份内存文本），不另造数据源
* 不新增 LLM 主观自判（复用已有机器信号，遵守 `references/review_gate.md`"声明≠核实"红线）

## 20.1 用例ID规范

格式：`<需求标识>_<功能缩写>_<序号>`

需求标识来自用户输入或索引文件匹配。功能缩写用于区分不同测试场景，但不拆分为多个文件（所有用例写入同一文件）。

示例：
* 订单创建-20260702_CREATE_001（需求标识="订单创建-20260702"，创建订单功能）
* 订单创建-20260702_PAY_001（订单支付功能）
* 支付重构_REFUND_002（需求标识="支付重构"，退款功能）

要求：全局唯一、同一需求标识+功能连续编号、不允许重复编号、不允许跳号。

## 20.2 关联需求ID规范

填写本用例对应的需求条目编号。
* 若需求文档提供编号：直接填写（如 REQ-ORD-001）
* 若未提供编号：填写"见需求文档<章节号或具体章节名>"（如 `见需求文档3.2订单创建`、`见需求文档订单创建节`），**禁止杜撰**
* **禁止笼统占位**：不得填写 `见需求文档'需求内容'`、`见需求文档`、`无` 等无法定位具体需求条目的值；每条用例须能追溯到具体需求条目（不同用例可指向同一条目，但不得全员同一笼统占位）

> `scripts/verify_cases.py` 关联需求ID追溯检测：全员均为笼统占位或全员相同占位 → 报"需求条目级追溯失效"。需求→用例覆盖闭环依赖此列可机器追溯。

## 20.3 关联规则规范

填写本用例验证的核心业务规则（自然语言短句），**并引用对应风险ID/测试点ID**（如 `R1:库存扣减、TP2:库存边界`），实现风险/测试点→用例的精确追溯。

示例：`R1:订单金额满减规则`、`TP3:支付幂等规则`、`R2:订单状态待支付→已支付流转`。

> ID 引用规则：用例关联规则列含 `R<序号>` 引用对应风险（见 `TestCases_*.md` 的"风险清单"section）、含 `TP<序号>` 引用对应测试点（见"测试点清单"section）。`scripts/verify_cases.py` 优先按 ID 精确追溯（R1 后非数字，避免 R10 误匹配 R1），未标注 ID 时降级为 token 兜底匹配（标注"疑似"）。

禁止杜撰规则；禁止留空。

## 20.5 用例名称规范

格式：`【模块】【功能】【场景，预期】`

示例：`【订单模块】【创建订单】【库存不足】【返回库存不足错误】`

要求：
* 四段必须齐全（模块/功能/场景/预期），禁止缺段、禁止空段
* 【模块】与"所属模块"列保持一致；【预期】须与 Then 列可观测断言呼应
* 禁止杜撰模块/功能；场景与预期须来自已确认需求或澄清台账，不得脑补
* 禁止使用模糊描述（如"测试成功""功能正常"），【预期】须具体可观测
* 【场景】与【预期】均需**简明扼要**：用最短语句表达核心场景与预期结果，避免冗长复述 Given/When/Then 细节。每个字段宜为一短语，不宜成句成段
  * 正确：【订单模块】【创建订单】【库存不足】【返回库存不足错误】
  * 错误（冗长）：【订单模块】【创建订单】【用户购物车有商品A001数量2但仓库实际库存仅剩1件时点击提交订单】【系统拒绝创建订单并返回库存不足错误码同时订单主存储中不产生任何订单记录且库存不扣减】
