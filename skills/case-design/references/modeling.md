# 9、规格建模规范（SDD）

每个功能必须抽象为：Feature、Rule、Constraint、Input、Output、State、Exception、Acceptance Criteria。

必须建立 Given / When / Then 模型。

并建立：状态模型、数据模型、权限模型、错误模型、接口契约模型。

### 事实来源标注与开发校对（提升规格可信度·强制）

SDD 中以下三块标注「事实来源」，并由 @开发 校对（开发拥有实现层的权威信息，文档状态机/异常阈值/接口契约常与实现有差异）：

| SDD 要素 | 事实来源 | 校对要点 |
| -- | -- | -- |
| State（状态机） | 实现状态机 vs 需求文档状态机 | 实际状态定义与合法/非法流转，以实现为准；文档状态机差异处须在用例反映 |
| Exception（异常） | 超时阈值/重试次数/补偿动作 | 实现细节，须由开发提供真实阈值/次数/间隔/动作 |
| Input/Output（接口契约） | 接口名/入参/出参/类型 | 真实字段名/类型，喂第8阶段测试数据，闭合 0.4 杜撰禁令 |

* 信息源：§5【技术实现摘要】（@开发提供）优先；未提供时由澄清台账（角色路由，见 `references/clarification.md`）向 @开发 征集
* 校对结果同步更新"规则建模"section 与受影响用例 G/W/T，保持三者一致（与"重走第4阶段须以已落盘规则建模+用例G/W/T为重建依据"机制天然衔接）
* 与运行模式正交：完整模式 @开发 校对后才进第5阶段；连跑/轻量模式以需求文档为假设继续，标注"待@开发校对状态机/异常/契约"

### 规则建模 section 来源标注（破自证循环·闭合 0.9·强制）

> 规则建模 section 沉淀为 `TestCases_<需求标识>.md` 的 section（见 `references/output_write.md` 追溯性 section），并供 `verify_cases.py` rule_coverage 校验"每类规则被用例覆盖"。该 section 由模型自写，**若无来源约束会被 rule_coverage 反向洗白为"已覆盖"**（根因：自证循环）。强制每条规则项标注来源，破该循环：

* 每条规则项须标注来源：`[来源:需求文档<章节号/章节名>/台账Q<序号>/假设A<序号>]`（三选一或多）
* 来源=需求文档：规则直接来自需求某章节（最可信）
* 来源=台账Q<n>：规则来自澄清台账用户已答复项（权威事实）
* 来源=假设A<n>：规则来自已登记假设（连跑/轻量 P2/P3，须回显进待确认问题与假设清单）
* 无来源标记的规则项 -> 疑似脑补规则，`verify_cases.py` 检查15 规则来源软提示，selfcheck 检查15 阻断（补来源或转问题/假设后重跑）
* 用例关联规则列引用 `R<序号>`/`TP<序号>` 时，对应规则/风险/测试点须有来源标记，形成"用例->规则->来源"完整链路（闭合 0.9 业务行为来源追溯）

### 接口契约模型与变更影响清单（契约驱动分支·强制）

当输入含接口文档（Swagger/OpenAPI/接口说明）时启用契约驱动分支：把接口分解为结构化契约，圈定本次需求涉及的**变更接口**，沉淀"变更影响清单"section（用例表之前，与规则建模/风险清单同级）。

# 13、Given / When / Then 规范

## 13.1 Given（前置条件）

必须明确：

### 用户状态
用户已登录 / 用户未登录 / 用户Token已过期

### 权限状态
普通用户 / 管理员 / 财务角色

### 数据状态
订单待支付 / 订单已支付 / 库存充足

### 系统状态
缓存存在 / 缓存不存在 / MQ正常

### 环境状态
第三方接口正常 / 第三方接口超时

## 13.2 When（操作步骤）

要求：一步一动作、明确测试数据、可自动化执行。

示例：
1. 打开订单创建页面
2. 输入商品编号A001
3. 输入购买数量100
4. 点击提交订单

### 步骤化子结构（优化）

复杂用例的 When/Then 若塞进单格会变成超大文本块，可读性差且 Excel 转换易乱。推荐采用步骤化子结构描述：

```text
步骤1：动作 = 打开订单创建页面
步骤2：动作 = 输入商品编号A001；预期 = 商品信息回显
步骤3：动作 = 输入购买数量100；预期 = 金额计算正确
步骤4：动作 = 点击提交订单；预期 = 接口返回200，订单状态为待支付
```

在表格单元格中以"步骤N：动作；预期"分行串联，保持一条用例一行，不拆行不合并单元格。

## 13.3 Then（预期结果）

必须覆盖：页面结果、接口结果、数据结果、状态结果、缓存结果、MQ结果、日志结果。根据场景按需选择。禁止过度断言。

### 断言完整性（#2·强制·防"测试通过却漏 bug"）

不完整 oracle（只断言响应、不断言副作用）是"测试通过却上线出 bug"的头号原因。状态变更类用例须**双重断言**：

* **状态变更类用例**（When 含 创建/支付/扣减/更新/删除/撤销/退款/发货 等会改变业务状态或数据的操作）的 Then **必须同时包含**：
  * 接口结果（HTTP 状态码/错误码/status 字段）——验证操作本身
  * 数据/状态结果（订单状态更新为已支付、库存数量减少N、余额变更）——验证副作用真实发生
* 仅断言"接口返回200"而不断言数据/状态副作用的用例判定不完整（检查13，见 `references/selfcheck.md`）
* `scripts/verify_cases.py` 软性提示：状态变更类用例 Then 仅含接口结果、缺数据/状态副作用

> 例：`When=创建订单`，错误 Then：`接口返回200`（缺库存扣减/订单状态断言）；正确 Then：`接口返回200且status=SUCCESS；订单主存储中订单状态为待支付；库存数量减少2`。

# 15.6 用例生成端强制约束（防类型单一化·防漏测·第8阶段）

用例生成（第8阶段）须遵循以下生成端约束（与校验端 `scripts/verify_cases.py` 闭环）：

* **方法→列映射**：测试类型/测试维度列必须按 `references/methods.md` 决策表"方法→列映射"填写，禁止单一类型覆盖（全"功能测试"即不合格）。`verify_cases.py` 测试类型种类<3 提示方法未落地。
* **生成前覆盖自检**：生成前对照覆盖矩阵（`references/coverage.md` 8.x）+ 第5阶段风险清单，自检每个 P0/P1 风险有对应方法用例、每个高价值维度（安全/幂等/契约/并发/状态机非法流转）有覆盖；缺口在内存内补齐后再写入。
* **关联规则含 ID**：关联规则列须引用风险ID/测试点ID（见 20.3），实现风险/测试点→用例精确追溯。
* **禁止类型单一化**：全表单一测试类型判定不合格（见 SKILL.md 0.8）。

## 20.1 用例ID规范

格式：`<需求标识>_<功能缩写>_<序号>`

需求标识来自用户输入或索引文件匹配。功能缩写用于区分不同测试场景，但不拆分为多个文件（所有用例写入同一文件）。

示例：
* 订单创建-20260702_CREATE_001（需求标识="订单创建-20260702"，创建订单功能）
* 订单创建-20260702_PAY_001（订单支付功能）
* 支付重构_REFUND_002（需求标识="支付重构"，退款功能）

要求：全局唯一、同一需求标识+功能连续编号、不允许重复编号、不允许跳号。

## 20.2 关联需求ID规范

填写本用例对应的需求条目编号。
* 若需求文档提供编号：直接填写（如 REQ-ORD-001）
* 若未提供编号：填写"见需求文档<章节号或具体章节名>"（如 `见需求文档3.2订单创建`、`见需求文档订单创建节`），**禁止杜撰**
* **禁止笼统占位**：不得填写 `见需求文档'需求内容'`、`见需求文档`、`无` 等无法定位具体需求条目的值；每条用例须能追溯到具体需求条目（不同用例可指向同一条目，但不得全员同一笼统占位）

> `scripts/verify_cases.py` 关联需求ID追溯检测：全员均为笼统占位或全员相同占位 → 报"需求条目级追溯失效"。需求→用例覆盖闭环依赖此列可机器追溯。

## 20.3 关联规则规范

填写本用例验证的核心业务规则（自然语言短句），**并引用对应风险ID/测试点ID**（如 `R1:库存扣减、TP2:库存边界`），实现风险/测试点→用例的精确追溯。

示例：`R1:订单金额满减规则`、`TP3:支付幂等规则`、`R2:订单状态待支付→已支付流转`。

> ID 引用规则：用例关联规则列含 `R<序号>` 引用对应风险（见 `TestCases_*.md` 的"风险清单"section）、含 `TP<序号>` 引用对应测试点（见"测试点清单"section）。`scripts/verify_cases.py` 优先按 ID 精确追溯（R1 后非数字，避免 R10 误匹配 R1），未标注 ID 时降级为 token 兜底匹配（标注"疑似"）。

禁止杜撰规则；禁止留空。

## 20.5 用例名称规范

格式：`【模块】【功能】【场景，预期】`

示例：`【订单模块】【创建订单】【库存不足】【返回库存不足错误】`

要求：
* 四段必须齐全（模块/功能/场景/预期），禁止缺段、禁止空段
* 【模块】与"所属模块"列保持一致；【预期】须与 Then 列可观测断言呼应
* 禁止杜撰模块/功能；场景与预期须来自已确认需求或澄清台账，不得脑补
* 禁止使用模糊描述（如"测试成功""功能正常"），【预期】须具体可观测
* 【场景】与【预期】均需**简明扼要**：用最短语句表达核心场景与预期结果，避免冗长复述 Given/When/Then 细节。每个字段宜为一短语，不宜成句成段
  * 正确：【订单模块】【创建订单】【库存不足】【返回库存不足错误】
  * 错误（冗长）：【订单模块】【创建订单】【用户购物车有商品A001数量2但仓库实际库存仅剩1件时点击提交订单】【系统拒绝创建订单并返回库存不足错误码同时订单主存储中不产生任何订单记录且库存不扣减】
