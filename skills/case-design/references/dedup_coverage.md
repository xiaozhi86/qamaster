# 16、测试点去重与过度设计剔除机制（强制）

## 去重原则

> v0.8.1：去重前**必须读取 Phase 8 用例的关联规则列**（`R<n>`/`RK<n>`/`TP<n>` 引用）**与 Phase 3 规则建模 / Phase 5 风险清单 / Phase 6 方法→类型映射 / Phase 7 测试点清单对照**——关联规则列引用不同（如一条引 R1+RK2、另一条引 R3+RK4）即视为不同测试意图，禁止合并。不得仅凭用例表字段（测试维度/类型/断言）去重而忽略上游追溯引用。

若多个测试点：规则相同、风险相同、断言相同、**测试维度相同、测试类型相同**，则合并。

### 维度/方法多样性保护（强制·防过度合并损失宽度）

去重不得跨测试维度或跨测试类型合并——即便规则/风险/断言相同：

* **测试维度不同**（如 边界验证 vs 异常验证 vs 并发验证）→ 视为覆盖不同维度，**禁止合并**
* **测试类型不同**（如 边界 vs 异常 vs 状态迁移 vs 并发）→ 视为方法不同，**禁止合并**
* 仅当规则+风险+断言+测试维度+测试类型**五者全同**时方可合并
* **矩阵类别不同**（契约类 A-F vs 规则类 G vs 场景类 H）-> 视为测试意图不同，**禁止合并**（即便断言相似，契约测 syntax、规则测 semantics、场景测 flow，互不替代；见 `references/methods.md` 统一接口测试矩阵）

> `scripts/verify_cases.py` 检查6 重复疑似按"关联规则+断言+测试维度+测试类型+用例等级"组合判定（用例表无独立风险列，以用例等级 P0-P3 代理风险），五者全同才报疑似重复；维度/方法/风险等级不同者不报，保护宽度。

## 过度设计剔除原则

删除：框架默认行为、无业务价值UI测试、重复边界测试、重复异常测试。

> "重复边界/异常测试"指**五者全同**的重复（见上去重原则）；不同维度/方法的边界或异常用例不算重复，不得以此为由删除。

## 优先保留

高价值、高风险、高信息密度测试点。

# 17、覆盖率控制机制（强制）

必须优先覆盖：主流程、核心规则、高风险路径、关键状态。

禁止：为覆盖率而覆盖、无限扩展边缘场景、无限扩展低风险测试点。

### 反向需求追溯（#4·闭合覆盖缺口·强制）

现有"用例→需求"追溯（每条用例填关联需求ID）只保证用例有归属，**不保证需求条目被覆盖**。须做反向追溯：

* 解析需求文档条目（按章节号/编号/小标题切分）→ 对每条需求条目查是否有用例引用（用例"关联需求ID"列）
* 未被任何用例引用的需求条目列为 **⚠ 未覆盖需求**，第10阶段内存内补齐对应用例后重跑
* 与运行模式正交：完整模式未覆盖需求须补齐才进第11阶段；连跑/轻量模式未覆盖需求记假设（"需求条目X未覆盖，待确认是否需补测"），不阻断
* `scripts/verify_cases.py` 增"需求条目追溯"软提示：列出未被用例引用的需求条目
* **#4-H 硬门（v0.6.0）**：REQ 已落盘且可解析时，需求条目被用例"关联需求ID"列引用比例低于 `coverage_gates.req_trace_min_ratio`（默认 1.0）即 exit=1——完整模式事实上要求全覆盖；连跑/轻量模式仍按上条记假设，但比例违约会硬阻断，须显式调整配置或补齐（推荐补齐）。

#### #4 显式强提示（闭合"静默跳过"盲区·强制）

> **根因**：原 #4 在"需求文档未落盘"或"无可解析章节"时返回 `(None,0)` 静默跳过，仅 stdout 打一行"跳过"，不阻断交付——导致"需求条目级覆盖未校验"无人知晓，"完整覆盖无遗漏"承诺失效。本节把静默跳过升级为**显式强提示**，闭合覆盖盲区。

* **触发条件**：`scripts/verify_cases.py` 的 #4 返回 `(None,0)`，分两类原因：
  * **(a) REQ 文件缺失**：第2参数未传或 `case-design-out/REQ_<需求标识>.md` 不存在 → 指向第0阶段步骤零未落盘（违反"REQ 强制落盘"，见 `references/phase0_manifest.md` 步骤零）
  * **(b) REQ 不可解析**：文件存在但 `parse_requirement_items_from_lines` 解析出 0 条目（纯散文无 `##` 标题、无 `REQ-xxx`/`需求N` 编号）→ 指向落盘格式不合规
* **提示内容（`verify_cases.py` 输出）**：`⚠ 需求条目级覆盖未校验（#4 静默跳过升级为显式强提示）` + 原因（缺失/不可解析）+ 影响（覆盖退化为依赖 LLM 自查+人工）+ 修复（落盘/补 `##` 标题后重跑）
* **门禁处理**：
  * 完整模式：#4 显式强提示须**消除后才进第14阶段**——补落盘 REQ（a）或补 `##` 标题分节（b）后重跑 `verify_cases.py`，直至 #4 真跑（`unc_req is not None`）；未消除不得声明"覆盖率全过"
  * 连跑/轻量模式：显式强提示不阻断推进，但须在交付摘要与审核话术标注"#4 未校验（REQ 缺失/不可解析），覆盖未做需求条目级闭环"，用户可见
* **交付摘要与审核话术**：`#4 反向需求追溯` 行填"未校验（原因）+ 待消除"而非"跳过"；`references/review_gate.md` 审核话术同口径

> 这是覆盖率的真实度量（需求里有没有整条被漏掉），比关键词维度统计更硬。但前提是 REQ 已落盘且可解析——故 #4 强提示与 `references/phase0_manifest.md` 步骤零"REQ 强制落盘"前后咬合。

#### Phase 10 检查点格式（v0.7.1·runtime 强制 gate 用）

runtime 在 Phase 10 出口门禁调 `verify_cases.py --phase-gate 10 .qamaster/case-design/<req_id>/checkpoint_10.md --req .. --ledger ..`（路径由 Runtime 按 `(workflow, req_id)` 分区解析，状态隔离不同需求）。**检查点文件必须复制 checkpoint_8.md 的完整 15 列用例表 + 追加覆盖分析**（不可只写"## 覆盖率 OK"摘要文档）。

**原因**：#4-H 需求追溯硬门校验的是用例表"关联需求ID"列对 REQ 条目的引用。若检查点无用例表，`parse_table_from_lines` 返回 None → `data_rows=[]` → 所有 REQ 条目"未引用" → 0% < 100% → 误报 FAIL。模型会误以为"关联需求ID 格式不对"反复改格式（无关修复），实则检查点格式错。

**格式违反**（必 FAIL）：检查点只写 `## 覆盖率\n\nOK\n` → phase-gate 报"[FAIL] 检查点格式不符: Phase 10 检查点必须含 15 列用例表"。正确做法：`checkpoint_10.md` = `checkpoint_8.md` 的用例表 + 覆盖分析（#4/#5/#6 追溯结果、缺口清单）。

**真实缺口 vs 格式错**（phase-gate 诊断区分）：
- 格式错（无用例表）：报"检查点格式不符"，须重写检查点
- 真实缺口（有用例表但某 REQ 条目未引用）：报"#4-H 需求条目 N 条、未被用例引用 K 条：\<条目\>"，须补齐对应用例的"关联需求ID"引用，或登记假设"条目X不在测试范围"

### 反向行为来源追溯（#5·闭合脑补缺口·强制）

> #4 只保证"需求条目被覆盖"，**不保证用例断言的业务行为有来源**。一条用例可引用真实需求编号、却在 Given/When/Then 里断言需求未定义的业务行为（状态流转目标/模态规则/约束值/异常机制），#4 照样通过。#5 补该缺口，闭合 0.3/0.9 脑补禁令。

* 抽取每条用例 Given/When/Then 中**断言的业务行为**（状态流转目标态 / 模态规则·允许·禁止·必须 / 约束值·上限·下限·最多 / 异常机制·回滚·补偿·重试·审批·校验 等）-> 逐条要求标注**来源四选一**（v0.8.0 由三选一升级，新增设计文档为合法来源）：
  * (a) 行为 token 出现在需求文档（或澄清台账已解决项）
  * (b) 关联规则列引用 `R<序号>`/`TP<序号>`（追溯到规则建模/风险清单/测试点清单已沉淀 section，且该规则项有来源标记）
  * (c) 关联规则列或用例名称含 `假设A<序号>`/`基于假设`（已登记假设）
  * (d) 行为 token 出现在设计文档（`DESIGN_<需求标识>.md`，含测试要点/字段映射/错误处理章节，v0.8.0·闭合设计文档行为无来源）
* 三者皆无 -> **⚠ 疑似无来源业务行为（脑补）**：不得静默保留，须转为**待确认问题**（P0/P1）或**假设**（P2/P3，登记入假设表并回显进待确认问题与假设清单），再重跑本追溯
* **规则建模 section 来源（破自证循环）**：规则建模 section 每条规则项须标注来源 `[来源:需求文档<章节>/台账Q<序号>/假设A<序号>]`；无来源标记的规则项 -> 疑似脑补规则（规则建模由模型自写，无来源约束会被 rule_coverage 反向洗白为"已覆盖"）
* 与运行模式正交：完整模式无来源行为必须停止转问题/假设；连跑/轻量模式 P0/P1 仍须停止，P2/P3 可转假设（登记+回显清单）后继续
* `scripts/verify_cases.py` 检查15/#5 软提示：列出疑似无来源业务行为（行号+行为信号）与无来源标记的规则项（需 §5 需求文档做 token 核对，未传则退回 (b)(c) 判定并注明）
> 这是"用例断言是否有据"的真实度量（行为有没有凭空捏造），与 #4（需求有没有被漏覆盖）互补，二者共同构成覆盖与可信的双向闭环。脚本为软性提示（NLU 限制，可能漏报/误报），模型须据提示逐条核验，负首要责任（见 selfcheck.md 检查15）。

### 反向接口追溯（#6·契约驱动分支·强制）

> 当输入含接口文档、启用契约驱动分支时执行；无"变更影响清单"section 则跳过。闭合"变更接口未做契约/规则/场景覆盖"缺口，与 #4（需求被覆盖）/ #5（行为有来源）互补，三者共同构成需求·行为·契约 三向闭环。

对"变更影响清单"section 的每个变更接口核查**三类覆盖**：

* **契约类（A-F）**：引用该 `API<序号>` 的用例须覆盖 入参存在性(必填字段不传/缺失) + 入参类型(类型错传) + 出参契约(错误码/状态码)
* **规则类（G）**：该接口"受影响规则"列的每个 `R<序号>` 须有用例引用覆盖（复用 rule_coverage 机制）
* **场景类（H）**：该接口"受影响场景"列的每个 `SC<序号>` 须有用例引用覆盖（新增 scenario_coverage）

* 无受影响规则 -> 跳规则类；无受影响场景 -> 跳场景类（不报缺）
* 缺类 -> ⚠ 软提示，第10/11阶段内存补齐后重跑（套 `references/methods.md` 统一接口测试矩阵对应类别行）
* 与运行模式正交：完整模式缺类须补齐；连跑/轻量模式记假设（"变更接口X缺契约/规则/场景覆盖，待确认"），不阻断
* `scripts/verify_cases.py` #6 软提示：列出缺类接口（需"变更影响清单"section 可解析，无法解析时跳过，不报错）
* **#6-H 硬门（v0.6.0）**：`coverage_gates.interface_three_class=full`（默认）时，任一变更接口缺类即 exit=1；`auto_light` 时连跑/轻量降为软告警（交付摘要须列缺口）、完整模式仍硬；`off` 关闭。

> 契约类只校验"变更字段"的 presence/type，不要求全字段（防爆炸，见 `references/methods.md` 三类收敛规则）。

### 反向测试点追溯（#7·闭合测试点级覆盖缺口·强制·v0.8.0）

> #4 只保证"需求条目被覆盖"，#6 只保证"变更接口三类覆盖"，**都不保证测试点清单每条 TP 被用例引用**。本节补该缺口，闭合"36 个测试点只覆盖 30 个用例静默通过"的事故（TP 漏映射机器看不见）。

* 解析测试点清单 section（`## 测试点清单`）每条 `TP<序号>` → 对每条查用例"关联规则"列是否引用 `TP<序号>`（ID 精确匹配，`TP1` 后非数字避免 `TP10` 误匹配；未标注 ID 时降级 token 兜底，标注"疑似"）
* 未被任何用例引用的 TP 列为 **⚠ 未覆盖测试点**，第10阶段内存内补齐对应用例后重跑（或在关联规则列补 `TP<序号>` 引用）
* 与运行模式正交：完整模式未覆盖 TP 须补齐才进第11阶段；连跑/轻量模式未覆盖 TP 记假设（"测试点 TPx 未覆盖，待确认是否需补测"），不阻断
* `scripts/verify_cases.py` 的 `testpoint_coverage()` 函数（既有·软提示）现升级为硬门判定并入 `coverage_gate_failures`
* **#7-H 硬门（v0.8.0）**：TP 清单存在（`tp_total>0`）且未覆盖比例 < `coverage_gates.tp_trace_min_ratio`（默认 1.0）即 exit=1——闭合 36→30 压缩。连跑/轻量模式 `testpoint_coverage=auto_light` 时降为软告警（交付摘要须列未覆盖清单）。

### 反向设计文档测试要点追溯（#8·闭合设计文档测试要点漏测·强制·v0.8.0）

> #4/#5/#6/#7 的追溯基准都是 REQ 需求文档，**设计文档自带的"测试要点"章节不是正式追溯源**——SpEL 扩展/Apollo 热更新/MDC 上下文/字段透传/安全脱敏这类"设计文档明列但需求文档没写"的要点从第2阶段起就不在覆盖矩阵。本节把设计文档升级为正式追溯源，闭合该缺口。

* 触发条件：第0阶段落盘了 `case-design-out/DESIGN_<需求标识>.md`（用户提供【设计文档】时提取其"测试要点"章节落盘，见 `references/phase0_manifest.md` 步骤零）。无 DESIGN 文件则 SKIP（不阻断，打 stdout 提示）
* 解析 DESIGN 文档"测试要点/测试点"章节（`## 测试要点`/`### 测试要点`/`## N. 测试要点`，穿透 `###` 子节），按表格行+编号列表切分条目 → 对每条查用例"关联规则"列或"用例名称"列是否覆盖（关键词命中；不扫 G/W/T 全文，避免通用词误判）
* 未被覆盖的设计文档测试要点列为 **⚠ 未覆盖设计文档要点**，第10阶段内存内补齐对应用例后重跑
* 与运行模式正交：完整模式未覆盖须补齐；连跑/轻量模式记假设，不阻断
* `scripts/verify_cases.py` 新增 `check_design_doc_testpoints`/`parse_design_testpoints`/`design_doc_testpoints_trace` 函数
* **#8-H 硬门（v0.8.0）**：DESIGN 存在且测试要点未覆盖比例 < `coverage_gates.design_doc_trace_min_ratio`（默认 1.0）即 exit=1。`--design` 参数传入 DESIGN 文件路径。
* **诚实披露**：#8 是关键词命中非语义保证（异形表述漏配即漏检），需按域维护 `domain_config.json` 关键词词表。终判归 LLM/人。

# 18、停止条件（强制）

满足以下条件立即停止：

* 核心规则已覆盖
* 高风险路径已覆盖
* 关键状态已覆盖
* 核心异常已覆盖
* 无高风险漏测点
* 无重复测试点
* 无过度设计

禁止继续生成低价值测试。

### 停止条件的机器可判前提（v0.6.0·事故修复·防"生成一点就停"）

> **根因**：停止条件被断章取义为"生成了核心用例即可停"——本次事故中模型仅交付 8 条"核心用例"即宣称完成，而第2阶段自建的覆盖矩阵 16 条需求条目只覆盖了 5 条。本节把停止条件加上**机器可判前提**，堵死主观缩水。

* **"已覆盖"的判定基准是覆盖矩阵，不是已生成的用例**：上述每条"已覆盖"均指**第2阶段测试覆盖矩阵/第3阶段规则清单/第5阶段风险清单中自建的全部条目**已被用例引用闭合，而非"已生成用例所涉及的条目"。
* **机器前提（verify_cases.py 覆盖硬门，不通过即 exit=1）**：
  * **#4-H 需求追溯硬门**：REQ 已落盘且可解析时，需求条目被用例"关联需求ID"列引用比例须 ≥ `coverage_gates.req_trace_min_ratio`（默认 1.0，即全覆盖）；
  * **#7-H 测试点追溯硬门**（v0.8.0）：测试点清单存在时，每条 TP 须被用例"关联规则"列引用，比例 ≥ `coverage_gates.tp_trace_min_ratio`（默认 1.0）；
  * **#8-H 设计文档测试要点追溯硬门**（v0.8.0）：DESIGN 存在时，其测试要点章节每条须被用例覆盖，比例 ≥ `coverage_gates.design_doc_trace_min_ratio`（默认 1.0）；
  * **safety_coverage 安全覆盖硬门**（v0.8.0）：REQ/DESIGN 含敏感信号词时，须有 ≥1 条测试类型=安全的用例；
  * **#6-H 变更接口三类硬门**：契约驱动分支下，变更影响清单每个接口的契约/规则/场景三类覆盖须齐全；
  * **RK P0/P1 风险硬门**：风险清单全部 P0/P1 须被用例"关联规则"列引用。
  （配置与模式语义见 `config/validation_rules.json` coverage_gates 与 SKILL.md"校验规则契约"节。）
* **"先生成核心用例、其余留待后续轮次"不构成停止条件满足**：一轮必须交付覆盖矩阵闭合后的完整用例集；token 预算只触发压缩/拆 PART/分响应，绝不触发缩减（见 `references/output_write.md` 反缩减硬条款）。
* 与运行模式正交：完整模式三门全硬；连跑/轻量模式按 `coverage_gates` 配置可降为软告警，但交付摘要"覆盖矩阵"行与"待确认问题"行必须显式列出未覆盖清单，禁止只写"待后续补充"。

# 26、需求规模分级（轻量路径）

> 避免小改动也走 15 步全流程。按变更风险与规模分三级，对应不同执行深度。

## 重型（完整流程）

* 新建模块 / 新核心业务链路
* 涉及 P0 风险（资金、支付、权限、状态流转、数据一致性）
* 跨需求、跨模块联动

执行：完整 15 步（SKILL.md 工作流 / 第23章 14 阶段）+ 全部门禁。

> **落盘默认单文件**：所有规模（含重型）的测试用例**默认写入一个文件** `case-design-out/TestCases_<需求标识>.md`（追溯性 section 全需求一份），便于整文件人工审核与 Excel 聚合。仅当写前实测合并体 > 24000 token（先压缩仍超）才拆最小 PART（`case-design-out/TestCases_<需求标识>_PARTn.md`，按风险排序、不按模块拆），拆分为异常出口而非默认（写前规模评估见 `references/output_write.md`）。

## 中型（标准流程）

* 已有模块新增功能点
* 涉及 P1 风险（并发、幂等、缓存一致性、接口契约）

执行：澄清（第1-2阶段）+ 规格建模（第4阶段）+ 风险分析（第5阶段）+ 用例生成（第6-8阶段）+ 自查门禁（第11阶段）；可合并建模阶段。

## 轻型（精简流程）

* 字段校验调整、文案变更、低风险参数调整
* 仅涉及 P2/P3

执行：澄清（第1-2阶段，如有缺口）+ 直接用例生成（第6阶段，等价类/边界值为主）+ 断言可观测自查（第11阶段）；可跳过完整规格建模（第4阶段）与覆盖矩阵（第10阶段）。

> 禁止：以"轻型"为由跳过需求澄清或输出模糊断言。轻型只缩减过程，不降低输出质量底线。
> 轻型仍须遵守：完整输出（一次性写入 .md，第13阶段）、人工审核门禁（第14阶段，完整模式下）、Excel 生成机制（references/excel.md，若用户要求 Excel）。

### 分级强制约束（与 phase0_manifest.md 步骤五一致）

* **P0 风险必须走重型**（完整15步），禁止以"小改"为由降级为中型/轻型
* **中型/轻型不得跳过自查（第11阶段）与审核门禁（第14阶段）**
* **轻型不得跳过需求澄清（第1阶段）**；中型/轻型只缩减过程，不降低质量底线（脑补禁令/断言可观测/存储合规/去重/覆盖率全不变）
* 规模判定在第0阶段（见 `references/phase0_manifest.md` 步骤五）；用户可显式声明"完整/连跑/轻量"覆盖

## 契约驱动分支（输入含接口文档时·与规模分级正交）

当第0阶段输入形态探测识别到接口文档（Swagger/OpenAPI/接口说明）时启用契约驱动分支：

* **变更接口数 = 0**（需求未触及接口）-> 不走契约分支，退回纯需求驱动
* **变更接口少**（1-3 个，P2/P3 为主）-> 轻型契约分支：契约类只做 presence(A)+type(B)+出参(E)，跳规则/场景类（无受影响时）
* **变更接口多**（>=4 或含 P0/P1）-> 重型契约分支：契约类全量(A-F)+规则类(G)+场景类(H)，按 `references/methods.md` 统一接口测试矩阵三类收敛规则执行

契约驱动分支与规模分级正交：可叠加（重型需求 + 契约驱动 = 完整15步 + 变更接口三类覆盖）。P0 风险仍守重型（不得以"小改"降级）。
