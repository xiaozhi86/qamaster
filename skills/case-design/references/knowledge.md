# 知识总结生成（审核通过后·强制）

> 本参考文件为知识总结生成（原 ch31）的**唯一细则来源**。第14阶段审核通过后读取本文件。
> **降本优化（Tier B）**：知识综合读取测试用例时，用 `scripts/project_cases.py <tc.md>` 抽取紧凑 5 列投影（用例ID/关联规则/用例名称/用例等级/测试类型）喂给 LLM，**禁止用 Read 把整份 15 列 TC.md 读进上下文**。综合来源逻辑不变（仍综合需求文档+台账+测试用例三来源），只改变"用例以何种粒度进入上下文"。需求文档与台账仍读全文（它们是主源）。

---

# 31.1 触发时机（强制）

* **触发点**：第14阶段（人工审核门禁）用户明确反馈"审核通过 / 无问题"后，**自动**触发（无需用户额外指令）
* **触发顺序**：审核通过 → 生成/更新知识总结 → 再询问是否生成 Excel
* **重要澄清**：此顺序仅为流程顺序，不代表依赖关系。知识总结与Excel是**两个独立的产出物**：
  * 知识总结 = 业务知识沉淀，生成后即落盘，与后续Excel无关
  * Excel = 测试用例表格（15列），生成时**只读取测试用例.md**，不读取知识总结
  * 用户确认生成Excel后，Excel生成只读取.md，不读取知识总结
* 审核未通过时**不**生成知识总结（用例尚在修改，知识总结会基于不稳定内容）

---

# 31.2 综合来源（强制）

知识总结须**综合以下全部来源**生成，禁止只取单一来源：

* 用户提供的**全部需求文档**（需求正文、原型图说明、流程图说明等）
* 澄清台账 `Clarification_Ledger_<需求标识>.md`（用户答复为权威事实）
* 已审核通过的测试用例 `<需求标识>.md`（本轮及前序轮次，**经 project_cases.py 投影读取**，反映实际业务场景与规则）

> 三者冲突时，以澄清台账 > 需求文档 > 测试用例为优先级（台账为用户确认的权威事实）。

# 31.3 文件名与元数据（强制）

## 文件名格式
`Knowledge_<需求标识>.md`

需求标识来自用户输入或索引文件匹配。示例：
* 需求标识="订单创建-20260702" → `Knowledge_订单创建-20260702.md`
* 需求标识="支付重构" → `Knowledge_支付重构.md`

文件名一旦确定，后续更新沿用同名，禁止重命名。位于当前项目根目录下的 `case-design-out/` 子目录（即 `case-design-out/Knowledge_<需求标识>.md`），与测试用例 .md、台账同目录。

## 文件元数据（强制）
知识总结文件开头必须包含元数据块：

```markdown
---
**元数据**
需求名称：<需求名称>
当前版本：v<major>.<minor>
首次生成：<YYYY-MM-DD>
最近更新：<YYYY-MM-DD>
更新模块：<模块列表，逗号分隔>
本轮变更：<新增/变更/删除/无>
来源统计：需求文档 X 条 / 澄清台账 Y 条 / 测试用例 Z 条
---
```

## 版本号规则

| 版本类型 | 规则 | 示例 |
| -- | -- | -- |
| major（主版本） | 新增模块时递增 | v1.0 → v2.0（新增支付模块） |
| minor（次版本） | 规则变更、字段变更时递增 | v1.0 → v1.1（变更金额规则） |

# 31.4 内容维度（必须覆盖·13维度）

知识总结须包含以下**13个固定维度**，章节顺序固定，不得调换。无相关内容的维度标注"本需求不涉及"，禁止删除章节：

| 序 | 维度 | 必须包含 | 可选包含 | 边界说明 |
| -- | -- | -- | -- | -- |
| 1 | 业务流程 | 主流程步骤、关键节点 | 分支流程、异常流程 | 不含流程图，仅文字描述 |
| 2 | 状态机 | 状态定义、合法流转 | 非法流转、终态标识 | 状态机以表格呈现，非法流转是核心 |
| 3 | 业务逻辑 | 计算逻辑、判定逻辑 | 公式推导 | 仅业务层逻辑，不含技术实现 |
| 4 | 业务规则 | 时间规则、数量规则、金额规则 | 其他约束 | 规则须可追溯到澄清台账 |
| 5 | 数据规则 | 字段校验规则、唯一性规则 | 精度规则 | 字段级校验，不含表结构 |
| 6 | 权限模型 | 角色定义、操作权限 | 数据归属 | 权限矩阵以表格呈现 |
| 7 | 异常处理 | 超时处理、重试机制 | 补偿机制、降级策略 | 仅业务层异常处理 |
| 8 | 配置项 | 可配置项名称、默认值 | 取值范围、开关项 | 需求明确提供的方可填写 |
| 9 | 存储信息 | 存储用途、涉及存储类型 | 关键字段 | 遵守 `references/quality_rules.md` ch12，未明确时用自然语言 |
| 10 | 接口信息 | 接口用途、入参摘要、出参摘要 | 错误码 | 遵守 ch12，未明确时用自然语言 |
| 11 | 上下游依赖 | 上游依赖、下游依赖 | 第三方接口、定时任务 | 依赖方+依赖内容+失败影响 |
| 12 | 变更历史 | 更新时间、更新模块、更新类型 | 更新内容摘要 | 每轮更新追加一条记录 |
| 13 | 待澄清项 | 待澄清问题列表 | 澄清状态 | 全部澄清时标注"本需求已全部澄清" |

### 各维度详细定义

#### 一、业务流程
- **主流程**：正常情况下用户/系统的操作步骤序列
- **分支流程**：条件触发导致的路径分支（如库存不足分支）
- **异常流程**：异常触发导致的处理路径（如服务超时）
- **格式要求**：步骤用编号列表（1. 2. 3.），分支/异常用"分支A-xxx"命名

#### 二、状态机
- **状态定义**：所有业务状态及其含义、是否终态
- **合法流转**：起始状态→触发事件→目标状态→前置条件
- **非法流转**：起始状态→尝试事件→拦截原因（**非法流转是状态机测试的核心，必须记录**）
- **格式要求**：三个表格（状态定义表、合法流转表、非法流转表）

#### 三、业务逻辑
- **计算逻辑**：金额计算、数量计算、积分计算等公式规则
- **判定逻辑**：条件判定规则（如库存是否充足的判定条件）
- **格式要求**：表格呈现（计算项/判定项 | 规则 | 精度/结果）

#### 四、业务规则
- **时间规则**：有效期、超时时间、时效限制
- **金额规则**：金额上下限、计算规则
- **数量规则**：数量上下限、批次规则
- **其他规则**：其他业务约束（如幂等规则）
- **格式要求**：分类列表，每类用小标题区分

#### 五、数据规则
- **字段校验**：业务字段级别的校验规则（长度、格式、范围）
- **唯一性规则**：唯一性约束
- **精度规则**：数值精度、时间精度
- **格式要求**：字段校验用表格（字段名 | 校验规则 | 示例值）

#### 六、权限模型
- **角色定义**：系统涉及的业务角色
- **操作权限**：角色×操作×对象的权限矩阵
- **数据归属**：角色×数据范围的归属规则
- **格式要求**：三个表格（角色定义表、操作权限表、数据归属表）

#### 七、异常处理
- **超时处理**：超时阈值与处理方式
- **重试机制**：重试条件、次数、间隔
- **补偿机制**：补偿触发条件与补偿动作
- **降级策略**：降级触发条件与降级方案
- **格式要求**：表格呈现（场景 | 阈值/条件 | 处理方式）

#### 八、配置项
- **可配置项**：可调整的业务参数（阈值、开关）
- **格式要求**：表格（配置项名称 | 用途 | 默认值 | 取值范围）

#### 九、存储信息
- **数据存储**：业务数据存储位置（遵守 ch12）
- **缓存**：缓存用途与内容（遵守 ch12）
- **消息队列**：消息用途与内容（遵守 ch12）
- **格式要求**：表格，未明确表名/字段名时用自然语言描述

#### 十、接口信息
- **涉及接口**：接口用途与入参/出参摘要（遵守 ch12）
- **错误码**：错误场景与错误码（需求明确时填写）
- **格式要求**：表格，未明确接口名时用业务语义描述

#### 十一、上下游依赖
- **上游依赖**：本模块依赖的上游服务/系统
- **下游依赖**：依赖本模块的下游服务/系统
- **第三方接口**：外部系统接口
- **定时任务**：定时任务名称与用途
- **格式要求**：表格（依赖方 | 依赖内容 | 失败影响）

#### 十二、变更历史
- **更新时间**：本次更新日期
- **更新模块**：本轮更新的模块
- **更新类型**：新增/变更/删除
- **更新内容摘要**：简要说明更新内容
- **格式要求**：表格，每轮更新追加一条记录，不得删除历史记录

#### 十三、待澄清项
- **待澄清问题**：尚未澄清的问题
- **涉及模块**：问题涉及的模块
- **风险等级**：P0/P1/P2/P3
- **状态**：待澄清/已澄清
- **格式要求**：表格，全部澄清时标注"本需求已全部澄清"

# 31.6 来源追溯机制（强制）

```text
知识条目 → 来源（需求文档/澄清台账/测试用例） → 用例ID（如有）
```

示例：
```text
知识条目：订单状态待支付→已支付流转
来源：澄清台账 Q2答复
用例ID：ORD_STATE_001
```

## 各章节追溯要求
每个知识章节末尾须增加"来源"小节，格式：
```markdown
## <章节名>来源

| 知识条目 | 来源类型 | 来源位置 | 用例ID（如有） |
| -- | -- | -- | -- |
```

## 追溯优先级

| 优先级 | 来源类型 | 说明 |
| -- | -- | -- |
| 1 | 澄清台账 | 用户确认的权威事实 |
| 2 | 需求文档 | 原始需求 |
| 3 | 测试用例 | 反映实际业务场景 |

## 追溯用途
- 知识变更时定位影响范围（哪些用例需要更新）
- 回归测试时快速定位变更模块的知识
- 知识冲突时验证正确来源

# 31.7 生成与更新机制（强制）

## 首次生成
`case-design-out/` 目录下无该知识总结文件 → 综合三来源生成完整知识总结（13章节齐全）

## 已存在时的更新策略

### 场景一：新增模块
1. 读取现有知识总结全部内容
2. 在对应章节追加本轮模块的知识条目
3. 元数据：major版本递增、更新模块追加、本轮变更=新增
4. 变更历史追加一条"新增"记录
5. 整表重写覆盖

### 场景二：规则变更
1. 读取现有知识总结全部内容
2. 定位变更章节，更新对应条目（标注变更标记）
3. 元数据：minor版本递增、本轮变更=变更
4. 变更历史追加一条"变更"记录
5. 整表重写覆盖

### 场景三：知识删除
1. 读取现有知识总结全部内容
2. 删除对应条目（或标注"已废弃"）
3. 元数据：minor版本递增、本轮变更=删除
4. 变更历史追加一条"删除"记录
5. 整表重写覆盖

## 多轮累积

# 31.8 写入机制（遵循完整输出）
* 知识总结在内存内综合三来源拼装完整后，用**单次 `Write`** 整体写入/覆盖

# 31.11 知识复用指引

## 知识总结的用途

| 场景 | 使用方式 |
| -- | -- |
| 回归测试 | 读取知识总结，快速定位变更模块与变更规则，识别影响用例 |
| 新需求设计 | 查询相关模块已有知识，复用已有规则/状态/权限定义（**须先过"相关性门槛 + 收益预检"**，见下） |
| 需求澄清 | 查询已有知识，避免重复提问已澄清问题 |
| 测试资产复用 | 知识总结作为"业务知识库摘要"输入（SKILL.md 输入协议） |

## 相关性门槛（跨需求复用·强制）

> 防止凭"话务/拨打/订单/支付"等泛业务域词联想，把**同域不同子系统**的知识总结误当作可复用上下文拉取。典型反例：CDR 监控告警系统（VOS/`vos_e_cdr`/呼叫中心 `collectionUrl`/告警冷却）与外呼任务系统（极光 `open-api/task/`任务状态机）虽同属话务域，但状态机/接口约定/上下游均无复用，读取仅增 token 与污染风险。

跨需求（**不同需求标识**）复用已有知识总结前，**必须**满足下列任一前提，方可读取其全文：

1. **同需求标识**：同一需求跨会话/跨轮次复用（真复用，第0阶段精确匹配命中本需求自身条目）。
2. **显式引用**：新需求文档或用户在【业务知识库摘要】中明确引用了该模块/该知识总结。
3. **系统/模块一致**：知识总结元数据"更新模块"/所属系统与新需求所属系统一致（须有证据，非词面联想）。

**禁止**：
- 仅凭泛业务域词（话务、拨打、订单、支付等）词面重叠即判定"相关"并读取全文；
- 把 `MANIFEST.md` 索引中同目录的其他需求条目默认视为可复用上下文逐一读取（逐一扫描禁令见 `references/phase0_manifest.md`）。

> 例外：用户在【业务知识库摘要】中**显式提供**的内容不适用本门槛（用户已判定相关），直接采用。

## 收益预检（读全文前·强制）

通过相关性门槛后、读取知识总结全文前，先做廉价预检：

1. 只读知识总结**元数据块**（需求名称/更新模块/来源统计）与各章节"来源"小节的模块清单；
2. 与本次需求的模块/规则/状态/接口清单比对，存在**可复用项**（同模块规则/同状态机/同接口约定/同上下游依赖）才读全文；
3. 无可复用项 → 跳过全文读取，记录"已预检·无复用"，不报错、不提问、不写文件。

> 全文读取遵循降本：知识总结正文可 Read，但仅在预检命中可复用项后；测试用例部分仍经 `scripts/project_cases.py` 投影读取（见 31.2）。

## 作为输入复用
当处理新需求、且通过上述相关性门槛与收益预检后，可将已有知识总结作为"业务知识库摘要"输入：
```markdown
【业务知识库摘要】

<<<已有知识开始>>>
<已有知识总结文件内容>
<<<已有知识结束>>>
```
模型读取后可复用已有规则定义，避免重复澄清。
