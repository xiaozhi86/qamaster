# 第0阶段：需求定位（必读·必须首先执行）

> 本参考文件为第0阶段（需求定位）与索引文件管理（原 ch6 第0阶段 + ch32）的**唯一细则来源**。进入第0阶段前读取本文件。SKILL.md 仅含流程入口与速记，细则以本文件为准。

---

## 设计目标

解决多需求场景下快速定位已有产出物。通过索引文件 `case-design-out/MANIFEST.md` 实现**一次读取定位所有相关文件**，避免逐一扫描所有文件。

## 输出位置约定（全局·强制）

> **所有需求产出物统一写入当前项目根目录下的 `case-design-out/` 子目录**（即 `<项目根目录>/case-design-out/`），包括：索引文件 `MANIFEST.md`、需求文档 `REQ_*.md`、澄清台账 `Clarification_Ledger_*.md`、测试用例 `TestCases_*.md`/`TestCases_*.xlsx`、知识总结 `Knowledge_*.md`。本约定为全局行为，贯穿第0阶段至第15阶段（Excel）及知识总结生成。

* **读取/写入统一加 `case-design-out/` 前缀**：凡涉及上述产出物的读写，路径均为 `case-design-out/<文件名>`
* **目录自动创建**：`case-design-out/` 目录不存在时，按需创建（首次写入产出物前）
* **索引表路径列**：填写**相对 `case-design-out/` 的文件名**（不含目录前缀），读写时统一加前缀
* **临时文件**：Excel 生成/校验用的 ad-hoc 脚本与中间产物（CSV/JSON/txt）同样置于 `case-design-out/` 下，用完即删（见 `references/output_write.md` ch30）
* **skill 自带资产除外**：`scripts/`、`config/`、`references/` 位于 skill 安装目录（`.claude/skills/case-design/`），**不在 `case-design-out/` 产出目录内**，不删除

## 核心原则

* **必须首先执行第0阶段**，禁止跳过直接进入第1阶段
* **必须先读取索引文件**，禁止逐一扫描所有文件来定位需求
* **索引文件是权威入口**：所有需求-文件映射以索引文件为准
* **一次读取定位**：禁止多次读取定位
* **匹配成功必须读取已有文件**：避免重复澄清/重复生成
* **匹配成功后必须立即更新索引状态=进行中**（已有需求）
* **新需求在第1阶段台账生成后新增索引**（status=进行中，路径确定性填全），第13阶段用例落盘更新进度，第14阶段审核通过后置为已完成
* **索引更新遵循完整输出**：整表 Write，禁止 Edit 增量，同一里程碑内禁止重复写（跨里程碑进度推进允许各自一次整表 Write）

## 执行步骤（强制）

### 步骤零：需求文档落盘（强制·#4/#5 反向追溯基准）

> **根因**：`scripts/verify_cases.py` 的 #4 反向需求追溯 / #5 业务行为来源追溯，**唯一可靠基准是已落盘的需求文档文件**（无文件 → 解析 0 条目 → 返回 `(None,0)` 静默跳过，覆盖退化为依赖 LLM 自查）。故用户的需求文档必须在进入第 1 阶段前落盘。

* **落盘时机**：在第 0 阶段读索引（步骤一）之后、步骤二匹配需求标识确定后，**立即**把用户提供的原始需求文档内容（无论用户内联粘贴于 `<<<需求文档开始>>>…<<<需求文档结束>>>`、还是给出文件路径）落盘为 `case-design-out/REQ_<需求标识>.md`
* **格式强制（为 #4 可解析）**：落盘内容须为可被 `parse_requirement_items_from_lines` 解析的结构——优先保留原始 Markdown 的 `## 二级标题`/`### 三级标题` 分节；若原始是纯散文/Word 转 markdown 无标题，落盘前**补加二级标题分节**（按需求条目切分，如 `## 订单创建` / `## 库存扣减`），使 #4 能解析出需求条目。文档根 `# 一级标题` 不计入条目（脚本跳过一级）
* **既有文件处理**：若 `case-design-out/REQ_<需求标识>.md` 已存在（已有需求匹配成功，步骤三），读入为权威基准，不覆盖；用户本轮若提供修订版需求，整表覆盖落盘并标注
* **与索引关系**：索引"需求文档"列填 `REQ_<需求标识>.md`（强制，不再"若有"）；落盘后步骤二的新增索引条目该列确定性填全
* **为何强制**：#4/#5 在第 8 出口 gate（写前内存内）与第 13 回读（写后）均以该文件为第 2 参数；不落盘则 #4 静默跳过、#5 退回无 token 核对的弱判定，"需求条目级覆盖未校验"无人知晓——这是"完整覆盖无遗漏"承诺的真实破口

### 步骤一：读取索引文件

**必须首先读取** `case-design-out/MANIFEST.md`：
* 索引文件存在 → 读入全部索引表
* 索引文件不存在（或 `case-design-out/` 目录不存在）→ 视为首次处理，按需创建 `case-design-out/` 目录并创建空索引文件，进入新需求完整设计流程

### 步骤二：匹配需求标识

根据用户提供的【需求标识】或从需求文档提取的关键词，在索引表中匹配：
* **精确匹配**：需求标识完全一致 → 定位已有需求，读取对应台账/用例/知识总结
* **关键词匹配**：需求简称匹配 → 定位已有需求，读取对应文件
* **无匹配**：视为新需求，进入完整设计流程

### 步骤三：定位已有文件（若匹配成功）

> 以下文件均位于 `case-design-out/` 子目录下：

* **澄清台账**：`case-design-out/Clarification_Ledger_<需求标识>.md`
* **测试用例**：默认 `case-design-out/TestCases_<需求标识>.md`（单文件，追溯性 section 全需求一份）；仅合并体压缩后仍 > 24000 token 才拆最小 PART `case-design-out/TestCases_<需求标识>_PARTn.md`（按风险排序、不按模块拆），此时索引列逗号分隔全部 PART 文件
* **知识总结**：`case-design-out/Knowledge_<需求标识>.md`

### 步骤四：判断处理模式

| 匹配结果 | 处理模式 | 后续流程 | 索引更新动作 |
| -- | -- | -- | -- |
| 索引文件不存在 | 新需求（首次） | 进入第1阶段完整设计 | 第1阶段台账生成后新增（进行中） |
| 无匹配 | 新需求 | 进入第1阶段完整设计 | 第1阶段台账生成后新增（进行中） |
| 精确匹配 + 已有台账 | 已有需求（增量） | 读取已有台账 → 第1阶段仅澄清新缺口 | **立即更新状态=进行中** |
| 精确匹配 + 已有用例 | 已有需求（修改） | 读取已有用例 → 按用户反馈进入修改流程 | **立即更新状态=进行中** |
| 精确匹配 + 已有知识总结 | 已有需求（复用） | 读取知识总结 → 作为业务知识库输入 | **立即更新状态=进行中** |

> **关键**：已有需求匹配成功后，**必须立即更新索引文件**（状态=进行中，更新时间=当前日期）。新需求在**第1阶段澄清台账生成后**新增索引条目（status=进行中，路径一次性确定性填全），第13阶段用例落盘后更新进度，第14阶段审核通过后置为已完成——确保跨会话中断时第0阶段能识别为"进行中"而非"新需求"，避免覆盖重生成已落盘产出物。

> **路径约定**：索引表"需求文档/台账文件/测试用例文件/知识总结"等列填写**相对 `case-design-out/` 子目录的文件名**（如 `TestCases_订单创建-20260702.md`，不含目录前缀）；实际读取/写入位置为 `<项目根目录>/case-design-out/<文件名>`，统一加 `case-design-out/` 前缀定位。本文件示例中的文件名均为相对 `case-design-out/` 的形式。

### 步骤五：判定需求规模（流程深度分级·方向4）

新需求或修改需求在进入第1阶段前，须判定需求规模，决定流程深度（见 `references/dedup_coverage.md` ch26）。用户可显式声明"完整/连跑/轻量"覆盖。

| 规模判定 | 触发条件 | 流程深度 | 阶段裁剪 |
| -- | -- | -- | -- |
| 重型 | 新建模块/新核心业务链路/涉及 P0 风险（资金、支付、权限、状态流转、数据一致性）/跨需求跨模块联动 | 完整 15 步 | 不裁剪，全部门禁 |
| 中型 | 已有模块新增功能点/涉及 P1 风险（并发、幂等、缓存一致性、接口契约） | 中型流程 | 可合并建模阶段（3-4），保留澄清+风险+用例+自查+审核门禁 |
| 轻型 | 字段校验调整/文案变更/低风险参数调整/仅 P2/P3 | 轻型流程 | 可跳过完整规格建模（第4阶段）与覆盖矩阵（第10阶段），保留澄清(1-2)+用例生成(6-8)+断言自查(11)+完整输出(13)+审核门禁(14) |

> **强制**：不得以"轻型"为由跳过需求澄清（第1阶段）或输出模糊断言；不得以"中型/轻型"为由跳过自查（11）或审核门禁（14）。轻型只缩减过程，不降低输出质量底线（脑补禁令/断言可观测/存储合规/去重/覆盖率等全不变）。P0 风险必须走重型（完整15步），禁止降级。

### 步骤六：输入形态探测（契约驱动分支判定）

读取用户提供的全部材料，探测是否含**接口文档**（信号：Swagger/OpenAPI JSON-YAML、`/api/` 路径、HTTP 方法表、入参/出参/错误码表、字段名+类型结构），判定是否启用契约驱动分支：

| 输入形态 | 判定 | 处理 |
| -- | -- | -- |
| 需求文档 + 接口文档 | 启用契约驱动分支 | 第4阶段建"接口契约模型+变更影响清单"，对变更接口按 `references/methods.md` 统一接口测试矩阵设计契约/规则/场景三类用例；第10阶段 #6 反向接口追溯 |
| 需求文档 + 新旧两版接口文档 | 启用契约驱动分支（diff 驱动） | 字段级 diff 圈定变更接口（最强信号） |
| 仅接口文档（无需求） | 契约兜底 | 全量接口按"新增接口"处理 + 澄清问 @开发 本次范围 |
| 需求文档（无接口） | 不启用 | 退回纯需求驱动（现有 15 步） |

* 变更接口圈定按 5 条信号合并去重（需求显式声明 / 接口文档变更标记 / 新旧 diff / 需求-接口交叉映射推断 / @开发 澄清兜底），详见 `references/modeling.md` 接口契约模型
* 契约驱动分支与规模分级（步骤五）、运行模式（SKILL.md 6.5）正交，可叠加
* 变更接口数 = 0 -> 不走契约分支，退回纯需求驱动

## 索引文件更新（强制·按里程碑更新）

> 设计原则：索引条目的**文件路径列**在需求标识确定后即**确定性可填全**，随进度变化的只有**状态**与"已落盘文件"。因此索引不绑定"某文件生成完毕"逐文件更新，而是按**里程碑**更新，确保跨会话中断时能正确识别"进行中"需求，避免被误判为新需求覆盖重生成。
> 状态语义：`进行中` = 明确的中间态（路径已填全，部分产出物已落盘）；`已完成` = 第14阶段审核通过的提交点。

| 触发点 | 场景 | 更新动作 | 状态变化 |
| -- | -- | -- | -- |
| 第0阶段（步骤零） | 需求文档落盘 `REQ_<需求标识>.md`（强制，新需求/已有需求均落盘或确认存在） | 落盘 REQ 文件（若用户内联提供或修订）；索引"需求文档"列确定性填 `REQ_<需求标识>.md` | — |
| 第0阶段 | 匹配成功（已有需求） | 更新状态和更新时间 | → 进行中 |
| 第1阶段 | 澄清台账首次生成（新需求） | **新增完整索引条目**，路径确定性填全 | → 进行中 |
| 第13阶段 | 测试用例 .md 落盘 | 更新更新时间 + **实际落盘文件清单**（多文件必做）；状态保持进行中 | 进行中 |
| 第14阶段审核通过后 | 新需求首次完成 / 已有需求修改完成 | 更新状态、时间、文件列表 | → 已完成 |
| Excel生成后 | - | **不更新索引** | 无变化 |

> 关键：索引文件在里程碑（第0/1/13/14阶段）多次整表 Write 更新；每次均为整表 Write 覆盖，禁止 Edit 增量。允许同一需求条目在生命周期内被多次整表 Write（每个里程碑一次），这**不违反**"禁止多次更新"——后者指"同一里程碑内重复写"或"Edit 追加"，而非跨里程碑的进度推进。

```

```

发生在进入第1阶段之前，标记正在处理、记录开始时间。

### 时机二：第1阶段 - 新需求澄清台账首次生成（新增索引条目）

> 解决跨会话定位缺口：新需求在台账生成后即写入索引（status=进行中），使会话中断后第0阶段能识别为"进行中"而非"新需求"，避免重生成覆盖已落盘的台账/用例。

```
1. 在内存中构建完整索引条目
2. 新增条目内容（路径列一次性确定性填全，禁止"待生成"占位；均填写相对 `case-design-out/` 的文件名）：
   - 需求标识：第0阶段确定
   - 需求名称：从需求文档标题提取
   - 需求文档：REQ_<需求标识>.md（**强制**落盘，见"时机零·需求文档落盘"；相对 `case-design-out/`）
   - 台账文件：Clarification_Ledger_<需求标识>.md（已生成）
   - 测试用例文件：TestCases_<需求标识>.md（默认单文件，确定性填写；仅合并体压缩后仍超 24000 token 才拆最小 PART `TestCases_<需求标识>_PARTn.md`，具体清单于第13阶段落盘后写回此列；均相对 `case-design-out/`）
   - 知识总结：Knowledge_<需求标识>.md（路径确定，尚未生成）
   - 状态：进行中
   - 更新时间：<当前日期 YYYY-MM-DD>
3. 整表 Write 覆盖（一次性新增，写入 case-design-out/MANIFEST.md）
```

发生在澄清台账落盘之后、进入第2阶段之前。需求标识与需求名称必须本阶段确定，避免后续里程碑改标识导致索引错位。

### 时机三：第13阶段 - 测试用例 .md 落盘（更新进行中进度 + 落盘文件清单）

```
1. 读取 case-design-out/MANIFEST.md

4. **更新"测试用例文件"列为实际落盘文件清单**（拆 PART 时必做）：
   - 默认单文件：`TestCases_<需求标识>.md`（相对 `case-design-out/`）
   - 仅压缩后仍超预算才拆 PART：逗号分隔全部 PART，如 `TestCases_<需求标识>_PART1.md, TestCases_<需求标识>_PART2.md, ...`（按风险排序，不按模块拆；均相对 `case-design-out/`）
5. 整表 Write 覆盖（写入 case-design-out/MANIFEST.md）
```

测试用例 .md **全部落盘**（位于 `case-design-out/` 下）并经 verify_md.py + verify_cases.py **逐文件回读通过后**更新（拆 PART 时在最后一个 PART 落盘回读通过后一次性写回全清单，同一第13阶段里程碑内仅此一次整表 Write，不逐文件追加写；单文件则直接写该文件名）。此步把实际落盘文件清单**及时**写回索引，确保跨会话中断在第13阶段后，第0阶段能按清单定位已存在用例、走"修改流程"而非"重新生成覆盖"。

> 跨会话兜底：若第0阶段读到 status=进行中但清单内用例文件在 `case-design-out/` 下不存在（如中断于第13阶段更新之前），按需求标识前缀在 `case-design-out/` 下定向查找 `TestCases_<需求标识>_*.md`（含 PART）定位实际文件——此为按前缀定向定位本需求文件，不属于"逐一扫描所有文件"。

### 时机四：第14阶段审核通过后 - 新需求首次完成 / 已有需求修改完成（提交点）

## 需求标识生成逻辑（强制·用户未提供时）

```
步骤一：提取需求简称
  1. 从需求文档标题提取核心关键词
  2. 去除特殊字符（保留中文、英文、数字、连字符）
  3. 保留核心业务词汇（如"订单创建"、"支付重构"）
  4. 简称长度建议 ≤ 15字符

步骤二：添加日期标识（可选）
  1. 格式：<需求简称>-<YYYYMMDD>，日期为开始处理日期
  2. 若本地无同名需求，可省略日期标识

步骤三：检验唯一性
  1. 在索引表中检查是否已存在相同标识
  2. 若存在：添加日期标识区分
  3. 若不存在：直接使用需求简称
```

唯一性检验流程：读取 `case-design-out/MANIFEST.md` → 检查索引表是否存在同名 → 存在则带日期 / 不存在则直接用 → 确定最终需求标识。

**强制**：需求简称必须来自需求文档核心内容禁止杜撰；需求标识必须唯一；带日期标识时日期必须准确；简称长度 ≤ 15字符。

## 强制要求（汇总）

* **所有产出物统一写入 `case-design-out/` 子目录**；索引文件固定位于 `case-design-out/MANIFEST.md`，读写产出物统一加 `case-design-out/` 前缀
* **需求文档 `case-design-out/REQ_<需求标识>.md` 强制落盘**（第0阶段步骤零）：用户内联提供或给文件路径的需求文档，必须在进入第1阶段前落盘为 `REQ_<需求标识>.md`（为 #4/#5 反向追溯提供唯一可靠基准；纯散文/无标题文档落盘前须补 `## 二级标题` 分节使其可被 `parse_requirement_items_from_lines` 解析，见步骤零格式强制）
* 必须首先读取索引文件；一次读取定位，禁止逐一扫描所有文件、禁止多次读取定位
* 匹配成功必须读取已有文件，避免重复澄清/重复生成
* 跨需求（不同需求标识）复用 `case-design-out/MANIFEST.md` 中其他条目的知识总结前，必须先过 `references/knowledge.md` §31.11 相关性门槛 + 收益预检；同域不同子系统（如 CDR 监控告警 vs 外呼任务系统）不构成相关，禁止凭泛域词联想读取
* 索引文件按里程碑更新（第0阶段匹配成功 / 第1阶段台账生成 / 第13阶段用例落盘 / 第14阶段审核通过）
* 索引更新遵循完整输出（每次整表 Write 覆盖，禁止 Edit 增量；同一里程碑内禁止重复写，跨里程碑进度推进允许各自一次整表 Write）
* 新需求在第1阶段澄清台账生成后新增索引条目（status=进行中，路径一次性确定性填全），确保跨会话中断可被第0阶段识别为进行中、避免被当作新需求覆盖重生成
* 已有需求在第0阶段立即更新状态为进行中
* 进行中条目是明确的中间态，不视为"半成品"；路径列禁止填"待生成"占位
* 需求标识必须唯一，必要时添加日期区分
* 索引文件禁止删除；文件命名必须包含需求标识

## 禁止（汇总）

* 完成后不更新索引文件
