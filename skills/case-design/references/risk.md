# 第5阶段：风险优先级体系（统一 P0-P3）

> 本参考文件为风险覆盖优先级（原 ch14）的**唯一标度来源**。第5阶段读取本文件并产出 P0-P3 风险清单。本 skill 中"P0-P3"专指风险，与 SKILL.md 合规红线不混用。
>
> **风险来源三源共验（提升发现力·强制）**：风险清单是下游一切（用例等级、方法深度、覆盖优先级、落盘顺序）的基石，须由三源共验而非 AI 单源脑补：
> * **需求推导**：AI 从需求文档推出的风险（既有能力）
> * **技术隐含@开发**：并发点/缓存击穿穿透/分布式事务边界/乐观锁冲突/MQ 乱序重复/缓存与 DB 一致性窗口——开发最清楚实现里的真实风险点
> * **业务领域@业务**：资金反向操作/监管红线/行业约束（金融清算时序、医疗剂量上限）/运营高频异常——业务最清楚真实运营中的风险
> * **缺陷反哺（#1·最高发现力）**：若 §5 提供【历史缺陷摘要】，每条历史缺陷映射为种子风险，强制每条→≥1 用例覆盖（见下"缺陷反哺"）
>
> 共验流程：AI 产出初稿并标注每条「风险来源」→ 经澄清台账（角色路由，见 references/clarification.md）征集开发/业务补充 → 合并去重 → 定稿落盘。与运行模式正交：完整模式 P0/P1 风险须角色共验才定稿；连跑/轻量模式角色未确认的风险记假设（"基于需求推导，待@开发/@业务确认"），不阻断生成，攒入交付报告。

## P0（最高风险，必须优先覆盖）

* 支付
* 资金
* 权限
* 数据一致性
* 状态流转
* 分布式事务
* 安全漏洞
* **敏感信息脱敏**（v0.8.0·显式列出）：通话内容/透传字段含客户敏感信息（手机号/身份证/银行卡/财务），AI 输出 summary/labels/evidence 可能含原文；全链路无脱敏 → 隐私泄露合规事故。涉敏感数据时 `safety_coverage` 硬门强制 ≥1 条安全类用例（见 `references/coverage.md` 8.9）
* 核心订单流程

## P1（高风险）

* 核心业务流程
* 接口契约
* 缓存一致性
* MQ一致性
* 并发更新
* 幂等控制
* 主业务链路
* 核心状态流转
* 权限体系

## P2（中风险）

* 普通业务流程
* 一般异常流
* 常规边界

## P3（低风险，按需覆盖）

* 低频功能
* 边缘场景
* 次要交互

> **接口契约风险的具体化（契约驱动分支）**：当输入含接口文档、启用契约驱动分支时，"接口契约 P1"风险由"变更影响清单"具体化——清单中每个变更接口即一个接口契约风险项，用例"关联规则"列引用 `API<序号>` 精确覆盖（见 `references/modeling.md` 接口契约模型）。变更接口 = 接口契约 P1 风险的受控子集，只测变更接口而非全量接口（防过度设计）。

## 缺陷反哺（#1·强制·最高发现力来源）

> 历史缺陷是"已证实的 bug 模式"，比人脑推测的风险更准。当 §5 提供【历史缺陷摘要】时强制执行；未提供则跳过本节（退回三源共验）。

* **映射**：每条历史缺陷（标题+根因+复现条件+所属模块）→ 映射到一个风险类别（资金/并发/状态/权限/缓存/MQ/异常/注入等）+ 标注「风险来源=缺陷反哺」
* **强制覆盖**：每条历史缺陷须有 ≥1 条用例覆盖（用例"关联规则"列引用对应风险ID，如 `R3:缺陷反哺-库存超卖`）；`scripts/verify_cases.py` 加"缺陷追溯"软提示（标注缺陷反哺来源的 P0/P1 风险未被用例覆盖时提示）
* **去重**：与需求推导/技术隐含/业务领域风险重合时合并，保留「缺陷反哺」来源标记（因已证实，优先级不降）

## 产出的风险等级用途

第5阶段产出的 P0-P3 风险清单用于：

* **用例等级标注**（用例等级取 P0-P3，见 `references/modeling.md` 20.6）

## 第5阶段出口机器 gate（风险来源·写前·内存内·有界自修）

> **根因**：风险来源漏标（P0/P1 标 @开发/@业务/缺陷反哺 但未在台账确认）原设计要拖到写后第13 `verify_cases.py` 风险来源提示才反向暴露，缺陷回流滞后。本 gate 在第5阶段风险分析完、进第6阶段前就地把"风险来源漏标/结构不全"拦住。

* **时机**：第5阶段风险分析完、进第6阶段前，内存内执行（零文件操作）
* **调用**：对风险清单 section 的 `lines` 用 `scripts/verify_cases.py` 的 `parse_section_rows(lines, "风险清单|风险分析|风险列表", ["风险ID", "风险等级"])` 取 `risk_rows`，再调 `risk_source_report(risk_rows)`（row-based，无需 keystone；第5阶段无用例表，不调 `run_inmemory`）
* **判定与自修**（≤2 轮）：
  * 风险清单结构不全（缺"风险来源"列值）→ 内存内补「风险来源」标注 → 重跑
  * P0/P1 标 @开发/@业务/缺陷反哺 但未在澄清台账见对应角色确认 → 提示台账角色确认（向 @开发/@业务/@业务 征集，走 `references/clarification.md` 角色路由）
  * 风险来源确无法判定 → **硬阻断**，转为台账Q 停止等角色确认；不静默假设放行
* **通过**→进第6阶段；此时风险清单已通过来源校验
* **运行模式正交**：连跑/轻量模式 P0/P1 角色未确认的风险记假设（"基于需求推导，待@开发/@业务确认"）放行（沿用 `risk.md` 三源共验机制），P0/P1 硬阻断仍停；完整模式须角色共验才定稿
* **与第8阶段出口 gate 独立**：第5 gate 只查风险清单 section 来源/结构，不查用例；第8 gate 用 `run_inmemory` 全量查用例表（含风险追溯）。两者检查项不相交，计数独立

## 第5阶段 critique 循环（P0 漏标·有界对抗式第二视角·Tier B）

> **根因**：机器 gate（上节）只能查"风险来源漏标/结构不全"，**查不出"该有却没有的风险"**——P0/P1 漏标是第5阶段最贵缺陷，机器无信号（风险清单本就不存在该条），只能靠对抗式第二视角发现。三源共验（风险来源三源共验节）已是多视角雏形，本节把它升级为**有界 critique 循环**。

### 机制（落盘前·内存内·有界）

在风险清单初稿产出、且通过出口机器 gate（上节）后，执行**独立 critique 遍**：换一个"挑刺视角"重新审视——"如果这个需求里漏了一个 P0/P1 风险，它会是什么？"，对照下列高发漏标方向穷举：

* **资金/数值**：负数、超限、精度丢失、资金反向操作、并发扣减超卖——是否在清单？
* **并发/幂等**：重复提交、重复消费、竞态、乐观锁冲突——是否在清单？
* **状态机**：非法流转、终态后操作、回滚异常、状态机绕过——是否在清单？
* **权限**：水平越权、垂直越权、Token 伪造/重放、权限绕过——是否在清单？
* **缓存/MQ 一致性**：缓存不一致、MQ 丢失/重复/乱序、最终一致性窗口——是否在清单？
* **时间边界**：跨天/跨月/跨年、Token 失效临界、有效期边界——是否在清单？
* **安全/脱敏**（v0.8.0·新增专项）：敏感字段脱敏（手机号/身份证/银行卡/财务）、AI 输出含原文敏感信息、SpEL 注入、配置热更新致参数泄露、日志/MDC/链路上下文丢失、密钥轮转、越权数据可见性、未授权调用（verifyAuth=false 暴露）——是否在清单？涉敏感数据时 `safety_coverage` 硬门强制 ≥1 条安全类用例覆盖。
* **设计文档测试要点**（v0.8.0·新增专项）：设计文档明列的测试要点（SpEL 扩展/容错、Apollo 热更新、MDC 上下文、字段透传 `_id`→`id`、字段命名转换 snake↔camel、内层 map 结构、请求 JSON root、Dubbo 双集群注册、HTTP 端点映射等）是否已映射为风险/测试点？见 `references/coverage.md` 8.11 + `references/dedup_coverage.md` #8。
* **历史缺陷反哺**：§5 若提供历史缺陷摘要，每条是否已映射为种子风险（缺陷反哺节强制）？

### 循环（≤2 轮·独立计数）

1. critique 发现**漏标风险** → 内存内补入风险清单（标注风险来源、风险等级）→ 重跑 critique
2. critique 发现**风险来源角色未确认** → 走台账角色路由（不属 critique 自修，转待确认问题，见下升级）
3. ≤2 轮后仍有漏标 → **升级阻断**：列出【风险漏标缺口清单】停止，转台账向 @开发/@业务 征集（P0/P1 阻断）；不得静默放行
4. **通过**→进第6阶段；此时风险清单已过机器 gate + critique 双校验

### 分工与边界（防循环嵌套·强制）

| 层 | 第5阶段出口机器 gate（上节） | 第5阶段 critique 循环（本节） |
| -- | -- | -- |
| 谁判 | `verify_cases.py risk_source_report` 客观 | LLM 对抗式第二视角 主观 |
| 管什么 | 机器能判：风险来源漏标/结构不全/角色未确认 | 机器判不了：P0/P1 漏标（该有却没有的风险） |
| 循环 | ≤2 轮（机器自修，独立计数） | ≤2 轮（critique 自修，独立计数） |
| 触发 | 机器信号驱动 | critique 驱动（无机器信号，靠第二视角） |

* **不重叠**：机器 gate 查"已列风险的来源"；critique 查"有没有漏列的风险"。两者检查项不相交
* **计数独立**：critique ≤2 轮与机器 gate ≤2 轮**各自独立计数**，不共享不嵌套；与第8 gate / 第11自查循环亦独立
* **顺序**：机器 gate 先跑（清来源/结构），critique 后跑（查漏标）——先客观后主观，critique 作用在已过来源校验的清单上

### 运行模式正交

* 完整模式：critique 必做；漏标 P0/P1 升级阻断
* 连跑/轻量模式：critique 仍做（低成本高收益）；漏标 P0/P1 仍阻断，漏标 P2/P3 可记假设放行
* **不放宽质量底线**：critique 只放宽"是否穷举"的判断深度，不放宽"脑补禁令/断言可观测/风险必须有来源"等底线

## critique 后移（G-FB2·Phase 7/8 漏标风险反哺·与 G-FB1 patch 联动）

> **根因**：第5阶段 critique 是 LLM 对抗式第二视角，**主观且无机器信号**——漏判一个 P0 风险时 critique 自身无客观兜底。而第7阶段测试点设计 / 第8阶段用例设计常常**暴露**第5阶段漏标的风险（如设计 TP 时发现"并发扣减超卖"该是一个独立 P0 风险却不在清单；写用例 Then 断言"终态后操作拦截"时发现状态机非法流转风险未列）。旧版只能 `fail --to 5` 粗粒度回退重跑整个第5阶段，代价过高致模型倾向"硬扛不补"。

### 机器信号（闭合"critique 无客观兜底"）

`scripts/verify_cases.py::check_testpoint_risk_orphans`（Phase 7/8 gate 软检查）：对测试点清单每条 TP，若其描述含 P0 域信号（资金/支付/权限/状态流转/数据一致性/并发/幂等/缓存/MQ 一致性）且**无对应 RK 引用**（风险清单未列该类风险）→ 报"疑似漏标风险：TPn 描述含 P0 域信号但风险清单无对应 RK"。这是第5阶段 critique 漏判的**客观机器信号**，补 critique 主观盲区。

### 反哺回路（不回退重跑·patch --to 5）

Phase 7/8 gate 发现漏标风险时，**优先用 G-FB1 `patch --to 5 --reason "补标 RK<n: <风险描述>，来源=<...>，第7/8阶段 TPn 暴露"` 登记增量反哺指令**——不回退 current_phase，指令注入当前阶段契约卡 `##PATCH_FEEDBACK##` 段，模型就地补标 RK 后重写本阶段产物（测试点/用例引用新 RK）。整阶段结构性问题（如风险清单全错）才用 `fail --to 5` 回退重走。

### 边界

* **不替代第5阶段 critique**：后移反哺是兜底，不是鼓励第5阶段少列风险——第5阶段 critique 仍是主防线，漏标越多第7/8阶段补标成本越高
* **计数独立**：第7/8阶段补标触发的第5阶段 gate 重跑（确认补标 RK 的来源/连续性）与第5阶段原 critique ≤2 轮独立计数
* **完整模式**：漏标 P0/P1 仍阻断（须补标 RK 并重过第5 gate 才放行）；连跑/轻量 P0/P1 亦阻断（P0 域风险不因模式放宽）
