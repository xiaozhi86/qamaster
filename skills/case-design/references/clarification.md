## Test Design Gap Analysis

在进入 Rule Modeling 前必须执行。目标：识别所有影响测试设计正确性的未知信息。

### 第一步（强制）：先加载澄清台账文件

执行任何缺口扫描**之前**，必须先读取澄清台账文件 `Clarification_Ledger_<需求标识>.md`：

* 台账文件存在 → 读入全部已解决问题及答复，作为**权威事实**
* 台账文件不存在 → 视为首轮，扫描后须创建该文件
* **本次只对"台账未覆盖 + 需求文档未覆盖"的缺口提问**；台账已解决的问题一律不再扫描、不再提问

> 需求标识来自用户输入（SKILL.md 输入协议）或从索引文件匹配（第0阶段）。
> 顺序强制：加载台账 → 排除已解决项 → 仅对剩余未知项做 Gap Analysis。禁止先全量扫描再事后过滤（易漏、易重复提问）。

## 输出格式

【待确认问题与假设清单】

> **统一展示（强制）**：待确认问题与假设**同列一张清单**向用户展示，加「状态」列区分阻断与否。假设**不再仅沉于交付报告**--必须在交付时回显进本清单，让用户在交付时一并可见可确认（闭合"假设埋在交付报告被忽略"）。问题与假设共用 ID 空间（Q=待确认问题、A=假设），便于事后定位。

| 问题/假设ID | 类型 | 问题描述 | 影响范围 | 风险等级 | 状态 | 建议回答角色 |
| ---- | -- | ---- | ---- | ---- | ---- | ---- |
| Q1 | 业务规则/状态机/数据/权限/异常/依赖 | <问题描述> | <影响范围> | P0/P1/P2/P3 | 待确认(阻断) / 假设(非阻断) | @开发/@产品/@业务 |
| A1 | 业务规则/状态机/... | <假设内容> | <影响范围> | P2/P3 | 假设(非阻断,事后确认) | @开发/@产品/@业务 |

* 状态=待确认(阻断)：按风险分级停止等待（P0/P1 全模式停；完整模式 P2/P3 亦停）
* 状态=假设(非阻断)：连跑/轻量模式下 P2/P3 缺口登记为假设，不阻断但须回显本清单+交付报告，提示用户事后确认

### 角色路由规则（强制·把问题抛给对口角色，减少答非所问往返）

每个问题须标注「建议回答角色」，把问题定向给最可能给出准确答案的角色：

| 问题类型 | 建议回答角色 |
| -- | -- |
| 数据规则 / 状态机 / 异常规则 / 上下游依赖 / 存储信息 / 接口契约·变更接口圈定 | @开发 |
| 业务规则 / 权限规则 / 优先级 / 范围 | @产品 |
| 领域约束 / 行业规则 / 真实运营场景 / 合规红线 | @业务 |

* 调用者可一次性把全部问题按角色标签转交各角色（如 "@开发 看 Q2/Q5、@业务 看 Q3"），**不增加提问轮次**
* 角色标签为路由建议，不阻断：任一角色代答仍接受，但记录"实际答者"以便回溯
* 与运行模式组合：完整模式按角色路由后逐条等回复；连跑/轻量模式 P2/P3 缺口记假设继续（假设登记表同步加「建议角色」列）

## 澄清阻断规则（按风险分级）

| 缺口风险等级 | 处理 |
| -- | -- |
| P0 | 必须停止，等待用户回复，禁止继续 |
| P1 | 必须停止，等待用户回复，禁止继续 |
| P2/P3 | 连跑/轻量模式下记为假设并继续（见 SKILL.md 6.5）；完整模式下停止提问 |

> 连跑/轻量模式下，P2/P3 缺口转为"假设"登记，回显进【待确认问题与假设清单】（状态=假设）+ 攒入交付报告，不打断流程但用户可见可确认。
> **降级模式补充（v0.6.0）**：无 Runtime 降级执行（SKILL.md 降级协议情形A）时，P2/P3 未闭环项只能登记假设继续，且交付摘要"待确认问题"行必须**逐条列出全部未闭环项**（ID+描述+建议角色），禁止只写"需后续澄清"概括——概括会让用户看不到缺口规模。

## 假设登记机制（连跑/轻量模式）

对未阻断的 P2/P3 缺口，记录为假设：

| 假设ID | 关联问题ID | 假设内容 | 假设依据 | 影响用例 | 建议角色 | 待确认标记 |
| -- | -- | -- | -- | -- | -- | 待确认 |

要求：
* 假设必须有合理依据（行业惯例/常见实现/最小惊讶原则），禁止无依据脑补
* **必须显式登记并在【待确认问题与假设清单】向用户展示**：假设不得仅存于交付报告或仅存于上下文。登记后须回显进清单（状态=假设），用户在交付时一并可见可确认（闭合"假设未在问题列表展示"）
* 受假设影响的用例须在**关联规则**列或 用例名称 中标注 `假设A1`/`基于假设A1`（机器可识别，供 verify_cases.py 检查15/#5 判定该行为已有登记来源），便于用户事后定位
* 「建议角色」列标注该假设事后应由哪个角色确认（@开发/@产品/@业务，路由规则同上），攒入交付报告提示用户事后定向确认
* 所有假设同时回显进【待确认问题与假设清单】+ 汇总进交付报告，提示用户事后确认

### 禁止静默推断（闭合 0.3/0.9 脑补禁令·强制）

> 0.3/0.9 禁止脑补业务规则。本节把该禁令在澄清层落地为可执行约束：

* **任何在用例 Given/When/Then 中出现、但未在需求文档/澄清台账/已登记假设中找到来源的业务行为（状态流转目标/模态规则/约束值/异常机制等）= 脑补**，判定不合格
* 发现脑补的**唯一合法处置**：转为**待确认问题**（P0/P1，停止等待）或**登记假设**（P2/P3，回显清单），**禁止**把推断当"显然/行业惯例"而既不提问也不登记就写入用例（静默推断）
* 「行业惯例/最小惊讶」**仅作为已登记假设的依据**，**不是**跳过登记的许可；引用行业惯例必须在假设表写明依据并回显清单
* `scripts/verify_cases.py` 检查15/#5 软性兜底：列出疑似无来源业务行为（未引用 R/TP、无 `假设A` 标记、且行为信号不在需求文档）与无来源标记的规则项，供 selfcheck 检查15 决策转问题/假设（见 `references/selfcheck.md`、`references/dedup_coverage.md` #5）

## 提问效率约束

* 一次性按类型批量列出全部问题，禁止逐条零散提问、多轮往返
* 每个问题须可独立回答，不依赖其他问题的答案
* 允许用户批量回复（如"Q1/Q3 按方案A，Q2 按方案B"）
* 同一会话已回答的问题不得重复提问

## 澄清台账机制（防重复提问·强制）

> 澄清是**有状态且持久化**的：用户的每次答复必须落盘为文件，并被后续所有环节复用。

### 台账必须落盘为文件（根本要求）

* 文件名：`Clarification_Ledger_<需求标识>.md`，位于当前项目根目录下的 `case-design-out/` 子目录（即 `case-design-out/Clarification_Ledger_<需求标识>.md`），与测试用例 .md 同目录
* 用户每次回答待确认问题后，**立即将答复写入该文件**（与写测试用例 .md 同等对待，是正式产出物）
* 该文件是澄清环节的**强制产出物**：澄清未落盘 = 澄清环节未完成
* 落盘原因：多轮设计、长对话上下文压缩会使"上下文里的记忆表"丢失；只有落盘文件才能在后续轮次被可靠重新读取

### 台账文件格式

```markdown
# 澄清台账 Clarification_Ledger - <需求标识>

| 问题ID | 类型 | 原问题 | 用户答复 | 状态 | 建议回答角色 | 登记轮次 |
| -- | -- | -- | -- | -- | -- | -- |
| Q1 | 数据规则 | 库存扣减时机？ | 下单即扣 | 已解决 | @开发 | 订单创建 |
```

要求：
* 用户答复一经落盘，**等同于需求文档的权威事实**，优先级与原始需求相同
* 台账文件在整个需求生命周期持续有效，跨模块、跨轮次、跨自修循环、跨对话压缩均以文件为准
* 用户后续修改答复 → 更新对应台账行（整表重写落盘），不新增重复问题

### 台账写入遵循完整输出

台账文件写入遵循完整输出原则（见 `references/output_write.md`）：整表在内存内更新完成后**一次性写入**，禁止多次追加/编辑。

### 一次性全局澄清

* Gap Analysis 在整个需求的**首轮执行一次**，产出完整待确认问题与假设清单并落盘台账
* 后续模块轮次、修改轮次、自修循环 **不重跑全局澄清**，只读台账文件
* 仅当出现"本轮新引入、且台账文件与需求文档均未覆盖"的缺口时，才补充提问该新缺口，并追加进台账文件

### 提问前强制查台账文件（防重复）

任何环节在提出待确认问题前，必须先**读取 `Clarification_Ledger_<需求标识>.md`** 比对：

* 问题已在台账文件且状态=已解决、答案**准确适用**本轮 → **禁止再问**，直接采用台账答案继续
* 台账**无**该问题，或台账有但答案**不准确/不适用/已过时**（如本轮需求变更使原答案失效）→ 把问题抛给用户，等待回答；用户回答后**立即将答复更新写入台账**（新增问题追加一行、已有问题更新对应行答案并标注更新轮次），整表一次性重写落盘
* 无法判断是否问过 → 读台账文件，不得"保险起见"重复问
* 上下文中找不到台账内容时 → **重新读取台账文件**，禁止因上下文丢失就重新提问

> 三步顺序强制：先查台账 → 台账无或不准确才问用户 → 回答后及时写回台账。任一步缺失即判定执行缺陷。
> 本机制为"全阶段暂停提问规则（台账优先）"在台账层的具体落地，二者一致。

### 禁止

* 重复询问台账文件中已解决的问题（违反即判定执行缺陷）
* 台账答案已不准确/过时仍沿用不重新提问（违反即判定执行缺陷）
* 用户回答后未及时更新写入台账（违反即判定执行缺陷，答复未留存）
* 把台账只存在上下文里而不落盘（多轮/压缩后必然丢失导致重复提问）
* 无视台账文件、对着原始需求文档重新扫描后再问同一问题
* 每个模块轮次都重跑全局 Gap Analysis 导致全局问题被反复提出
* 自修/修改循环中重新触发已关闭问题的提问

### 跨会话说明（台账的生命周期）

* 澄清台账已落盘为 `case-design-out/Clarification_Ledger_<需求标识>.md`，**跨会话仍然有效**
* 新会话处理同一需求时：只要该文件存在于 `case-design-out/` 目录，Gap Analysis 第一步即读入，不重复提问
* 若文件不存在（如换了项目目录/首次处理）→ 视为首轮，重新澄清并创建文件，属正常行为
* 亦可将已确认答案回填进需求文档，双重保险

## 全阶段暂停提问规则（台账优先·强制）

> 适用于**每个阶段**（第1-14阶段及自修循环）。凡任一阶段执行中遇到需暂停等待用户回答的问题（澄清缺口、规则缺失、状态机歧义、数据口径、权限边界、异常处理、风险判定、断言依据等），必须先走台账，再决定是否问用户。

按以下顺序处理（禁止跳过任一步）：

1. **先查台账**：读取 `Clarification_Ledger_<需求标识>.md`，比对当前问题是否已有记录
2. **台账判定**：
   * 台账有该问题且状态=已解决、答案**准确适用**于本轮 → **直接采用台账答案**，不再问用户，继续推进
   * 台账**无**该问题，或台账有但答案**不准确/不适用/已过时**（如需求变更使原答案失效）→ 把问题抛给用户，暂停等待回答
3. **回答后及时写台账**：用户给出回答后，**立即**将答复更新写入台账文件（新增问题追加一行；已有问题更新对应行答案并标注更新轮次），整表一次性重写落盘（遵循完整输出），再继续推进

> 判定"答案是否准确适用"须结合本轮上下文：若本轮需求范围/规则已变化导致台账原答案不再成立，视为"不准确"，须重新提问并更新台账，禁止沿用失效答案。
> 违反（未查台账直接提问 / 答案不准确仍沿用 / 回答后未及时写台账）即判定执行缺陷。
