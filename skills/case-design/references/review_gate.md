# 21.5 人工审核门禁（强制）

## 知识总结与Excel的关系（必读·澄清误解

> 本节澄清一个常见误解：**知识总结与Excel是两个完全独立的产出物，无依赖关系**。

| 产出物 | 数据源 | 内容 | 生成时机 |
| -- | -- | -- | -- |
| 知识总结 `Knowledge_*.md` | 需求文档+澄清台账+测试用例 | 业务知识沉淀（13维度：流程/状态机/规则等） | 审核通过后自动生成 |
| 测试用例Excel `TestCases_*.xlsx` | **仅测试用例.md** | 测试用例表格（15列：用例ID/Given/When/Then等） | 用户确认后生成 |

**关键澄清**：
* Excel生成**只基于测试用例.md文件**，不涉及知识总结、不涉及台账
* 知识总结是**业务知识资产**，Excel是**测试用例资产**，两者内容完全不同
* 流程顺序"知识总结→Excel询问"是**顺序执行**，不是**依赖关系**
* 知识总结生成完成后，Excel询问只是询问用户是否需要Excel格式，Excel生成只读取.md

## 完整流程

```
完整生成 Markdown（遵循完整输出原则，一次性写入；多文件拆分则全部文件连续落盘 + 回读通过后统一审核，不在文件间停顿，见 references/output_write.md 拆分多文件自动续跑）
↓
提示用户对 .md 测试用例文件进行人工审核（多文件时一次审核覆盖全部拆分文件，覆盖摘要/缺口按全部文件聚合）
↓
等待用户反馈
↓
用户反馈有问题 → 按 references/output_write.md "起点判定" 确定重走起点 → 重入主执行流程从该阶段依次执行至第14阶段 → 重新提示审核
用户反馈无问题 / 审核通过 → 自动生成/更新知识总结（references/knowledge.md，独立产出物）
                          ↓
                          询问是否生成 Excel（仅询问，不影响知识总结）
                          ↓
                          用户确认生成 Excel → 仅读取测试用例.md → 按 references/excel.md 生成Excel
                          用户不生成 Excel → 流程结束（知识总结已落盘）
↓
（若用户确认）生成 Excel（仅基于.md，与知识总结无关）
```

## 禁止
* 未经人工审核直接生成 Excel
* 默认审核通过
* 跳过审核提示
* 用户未明确反馈即推进流程
* 误解Excel需要知识总结作为输入（Excel只基于.md）
* 在Excel中输出知识总结内容（Excel只输出测试用例15列）

## 强制
* .md 生成后必须显式提示用户进行人工审核
* 完整模式下必须等待用户明确反馈"无问题"或"审核通过"，未收到明确通过反馈前禁止进入后续流程
* 连跑/轻量模式下可标注"待人工审核"后自动推进；多文件拆分时全部文件连续落盘后统一标注待审核、不在文件间停顿（P0 风险在统一审核门禁中覆盖，不再逐文件早审，见 SKILL.md 6.5 与 25 轮次优先级、references/output_write.md 拆分多文件自动续跑）
* 审核反馈若有问题，按 `references/output_write.md` "起点判定"确定重走起点，**重入主执行流程从该阶段起依次顺序执行至第14阶段**，重新走完整输出并再次提示审核
* 审核通过后须**自动生成/更新知识总结**（`references/knowledge.md`），这是独立产出物，与后续Excel无关
* 知识总结生成完成后，询问是否生成 Excel；**Excel生成只读取测试用例.md，不读取知识总结**

```

【脚本校验摘要】（逐项取自 verify_cases.py 回读输出对应行，填实际数值，禁止只填"通过"）：

【覆盖缺口】（来自 verify_cases.py，供审核聚焦；无则填"无"）：[列出 ⚠ 项，如"幂等=0、安全=0、某P0/P1风险未覆盖、某测试点未覆盖、异常子类缺N类、缺失风险/测试点清单 section、过度设计疑似N条、需求追溯失效、状态变更类用例缺数据/状态副作用断言（检查13）、未覆盖需求条目（反向追溯#4）、风险来源@角色未在台账确认、存储名不在技术实现摘要清单（检查9增强）、**无来源业务行为/无来源标记规则项即疑似脑补（检查15/#5）**"，无缺口填"无"]

审核通过后回复"无问题"或"审核通过"，将生成知识总结并询问是否需要Excel格式；

```

> 覆盖摘要、脚本校验摘要与缺口均取自第13阶段 `scripts/verify_cases.py` 的回读输出，话术中填实际数值，禁止只填"通过/无"而无依据。**脚本校验摘要五项**须从 verify_cases.py 输出的对应行直接取（"检查13 断言完整性: 疑似 N 条" / "检查9增强 存储schema交叉: 疑似 N 条 或 跳过" / "待台账角色确认的 P0/P1 风险（N 条）" / "反向需求追溯 #4: 未被用例引用 N 条 / 全部覆盖 / 未校验(REQ缺失或不可解析,待消除)" / "检查15 业务行为来源追溯(#5): 疑似 N 条 或 跳过"）。**#4 反向需求追溯行**：REQ 已落盘且可解析时填"未引用 N 条/全部覆盖"；REQ 缺失或不可解析时填"未校验(原因,待消除)"——此为显式强提示（见 `references/dedup_coverage.md` #4 显式强提示节），完整模式须消除后才算审核通过、连跑/轻量模式标注待消除后推进，**禁止填"跳过"隐瞒**。缺口为软判定提示，不阻断审核；人工可据此判断是否要求补齐后再审。**【待确认问题与假设清单】**为强制回显项：假设须在此向用户展示（闭合"假设未在问题列表展示"），人工审核重点核对假设是否成立、有无脑补业务行为。
> **多文件拆分**：话术"共 N 条"与覆盖摘要/缺口按**全部拆分文件聚合**（N = 各文件用例数之和，各文件 verify_cases.py 输出合并），一次审核覆盖全部文件；文件清单在话术中列全（如 DETECT x 条 / ALERT y 条 / WHITELIST z 条）。

> 说明：人工审核属于写文件之后的交互环节，不纳入 `references/selfcheck.md` "输出前自查"（自查是写前可判定项）。审核门禁作为流程节点存在于本节与 SKILL.md 25 流程总览。

## 测试用例生成前必须满足

### 勾选纪律（强制）
* 每勾选一项必须基于**可核验依据**，而非默认通过
* 勾选时须能指明核验方式（如：逐条核对关联需求ID非空、逐条核对断言含可观测结果）
* 必须实际逐项执行核实，禁止"一气勾完所有框"

> 禁用模式（出现即判定门禁失败，等同于未自查）：

| 模式 | 问题 |
| -- | -- |
| 批量声明"已全部自查通过" | 无逐项依据，等于跳过自查 |
| 仅声明结论不附核验依据 | 声明≠核实 |
| 以"时间紧/已生成完整"为由跳过逐项 | 禁止跳过 |
| 勾选后发现某项实际未做，仍保留勾选 | 禁止，必须如实改为未通过并进入门禁失败处理 |
